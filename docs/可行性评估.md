# 电商竞品情报分析平台 — 可行性评估

> 评估日期：2026-09-28
> 评估对象：原始需求文档（数据采集 / 清洗存储 / 可视化 / AI 分析 / 导出告警 / 进阶功能）

---

## 一、总体判断

**选题方向是对的**，理由：

- 数据采集 → 清洗 → 存储 → 可视化 → AI 分析 → 出口（导出/告警）是一条**完整闭环**，面试时能一口气讲 20 分钟不重复
- 每一环都有可深挖的技术决策点（见文末"面试亮点"），不是 CRUD 堆砌
- 与你已有的 aiwenda 项目（FastAPI + 智谱 GLM + SSE）技术栈重合，可以复用经验，学习成本低

**但是**，原方案里有 **3 个会导致项目烂尾的硬坑** 和 **2 个逻辑漏洞**。如果按原文照做，会在第 1 周就卡死在采集上，后面 4 个模块全部没时间做。

核心结论一句话：**把项目定位从"爬虫项目"改成"数据管道 + 分析项目"，采集只是入口，不是主体。**

## 二、三个硬坑

### 坑 1：1688 和淘宝是一家的（最严重）

原文说"别碰淘宝/京东的反爬，你搞不定"，这个判断完全正确 —— 但紧接着推荐 1688，这是个致命误判。

**1688 是阿里巴巴集团旗下的 B2B 平台**，和淘宝共用同一套风控体系（阿里系）：

| 反爬手段 | 说明 |
|---|---|
| 滑块验证码 | 阿里自研，行为轨迹检测，无头浏览器一样拦 |
| 请求签名 | `_m_h5_tk` / `sign` 参数由 JS 动态生成，需要完整逆向 |
| 登录态强依赖 | 商品详情、价格、销量大量内容登录后才可见 |
| 设备指纹 | Canvas / WebGL / 字体列表检测，Playwright 默认指纹会被识别 |

结论：**你会在 1688 上花掉 80% 的项目时间，且大概率抓不到稳定数据。** 难度和淘宝同级，不是"替代品"，是"同一个坑"。

→ 替代方案见 **第四节：数据源方案**

---

### 坑 2："Playwright 比 requests 稳" 这个说法是错的

准确的技术表述应该是：

| 数据所在位置 | 正确工具 | 原因 |
|---|---|---|
| XHR / JSON 接口 | `httpx` 直接请求接口 | 快 10–50 倍，稳定，无浏览器开销 |
| 服务端渲染的 HTML | `httpx` + `parsel`/`lxml` 解析 | 够用，轻量 |
| JS 客户端渲染 | Playwright | 只有这种情况才需要真浏览器 |
| 有反爬指纹检测 | Playwright + 指纹伪装 | 不得已才用 |

真实工程里是**分层降级**：

```
尝试解析 JSON 接口  ──失败──▶  尝试解析 HTML  ──失败──▶  Playwright 渲染
     (最快)                        (中等)                  (最慢，最后手段)
```

**面试时讲这个分层策略，比讲"我用了 Playwright"高一个档次。** 前者体现判断力，后者只是工具名。

**Playwright 的真实成本**（原文没提）：

- 一个 Chromium 实例占 **300–500 MB 内存**
- 并发 5 个 page 就 2 GB+，Windows 上很容易卡死或触发 OOM
- 必须用 `asyncio.Semaphore` 限制并发（建议 2–4 个）
- 启动开销约 1–3 秒/实例，所以要让 browser 常驻、只新建 context/page

### 坑 3：`BackgroundTasks` 不适合长任务

`BackgroundTasks` 的设计意图是"请求结束后顺手做点小事"（发一封邮件、写一条日志）。用它跑几分钟的爬取任务会出四个问题：

1. **阻塞服务**：同步任务会占用 uvicorn 的 worker 线程
2. **无进度反馈**：前端不知道爬到第几个商品了，只能干等
3. **无法取消**：用户点了"取消"，任务还在跑
4. **重启即蒸发**：服务一重启，所有进行中的任务消失

→ **替代：任务落库 + 独立 worker 进程**

```
API 收到采集请求
   └─▶ 往 task 表插一条记录（status=pending），立即返回 task_id
         └─▶ 独立 worker 进程轮询 task 表，取任务执行，实时更新 progress
               └─▶ 前端轮询 /api/tasks/{id} 拿进度
```

MVP 阶段用 SQLite 当队列就够，**不要上 Celery**（需要 Redis/RabbitMQ，对单机项目是过度设计）。面试话术：

> "我评估过 Celery，但引入 Redis 会增加部署复杂度，我的数据量是每天几千条、单机运行，用 SQLite 做任务队列 + 独立 worker 进程完全够用。这是有意识的取舍，而不是不会用 Celery。"

## 三、两个逻辑漏洞

### 漏洞 1：「价格趋势折线图」没有数据可画

原文写"价格趋势折线图（同一商品多次采集的价格变化）"—— 但如果你**今天才开始采集**，数据库里只有**一个时间点**的数据，折线图画出来是一个点。

趋势分析是这个项目的核心卖点之一，不能没有。三个替代方案（按推荐度）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 用现成历史价格** | SMZDM 的"好价"页面本身就带历史价格和发布时间 | 数据真实 | 覆盖商品有限 |
| **B. Mock 历史数据生成器** ⭐ | 写一个 seeder，按真实价格分布规律（随机游走 + 促销跳变）生成过去 90 天的价格序列 | 演示效果满分，可控，永远能跑 | 数据是模拟的 |
| **C. 时间压缩** | 定时任务改成 5 分钟一次，跑一上午就有几十个数据点 | 全真实 | 只能演示短期，且耗时间 |

**推荐 A + B 组合**：真实数据用 A，趋势演示用 B 补足。面试时如实说明："趋势功能的数据源是模拟生成的，用于验证分析 pipeline；真实采集部分我实现了完整的分层降级策略。" —— 诚实且专业，比含糊其辞强得多。

---

### 漏洞 2：「增量采集」的定义不成立

原文写"记录每个商品的 链接+最后采集时间，只更新有变化的或新增的商品"。

**问题：不重新抓取，你怎么知道有没有变化？** 这个描述在逻辑上无法实现。

正确的增量策略是**两个层面**，分开处理：

| 层面 | 策略 | 效果 |
|---|---|---|
| **列表页增量** | 抓到的商品链接，与数据库已有链接比对，只对**新增**的入库 | 这才是真正的"增量" |
| **详情页刷新** | 按 `last_crawled_at` 排序，只重抓超过 TTL（如 24 小时）的商品 | 这才是"只更新有变化的"的可行实现 |

伪代码：

```python
# 第一层：列表页只处理新链接
existing_urls = db.get_all_product_urls()
new_urls = [u for u in crawled_urls if u not in existing_urls]
# 第二层：老商品按 TTL 决定是否重抓
stale = db.query_products(last_crawled_before=now - timedelta(hours=24))
targets = new_urls + stale
```

面试时把这两层讲清楚，是明确的加分项 —— 说明你真的想过这个问题，而不是背概念。

对比"我爬了淘宝"（吹牛，面试官一问细节就露馅），这个话术的可信度和专业度高得多。

## 五、能够做、且值得做的部分

### ✅ 1. SQLite 表结构设计

完全可行，且是很好的展示点。建议表结构：

| 表名 | 用途 |
|---|---|
| `products` | 商品：标题、URL、当前价、销量、店铺 ID、`last_crawled_at` |
| `price_history` | 价格变动历史：商品 ID、价格、采集时间 |
| `shops` | 店铺：名称、平台、商品数 |
| `crawl_tasks` | 任务：状态、进度、开始/结束时间 |
| `alerts` | 告警规则与触发记录 |
| `analysis_reports` | AI 分析报告缓存（带数据指纹） |

**必须注意**：开 WAL 模式。

```sql
PRAGMA journal_mode=WAL;
```

原因：后台 worker 写入 + FastAPI 读取会争抢写锁。WAL 模式下读不阻塞写、写不阻塞读。**这个细节面试能聊。**

数据量评估：单机采集，每天几千条、累计几十万条以内，SQLite **完全够用**，不要上 PostgreSQL。

### ✅ 2. 数据清洗 —— 这是项目最值钱的部分

"已售1万+" → `10000` 这类脏数据解析，是**最能体现工程能力**的地方，因为它需要处理大量边界情况：

| 输入 | 期望输出 | 陷阱 |
|---|---|---|
| `已售1万+` | 10000 | |
| `1.2万` | 12000 | 小数 |
| `3千+` | 3000 | 中文单位 |
| `9999` | 9999 | 纯数字 |
| `暂无` / `--` | `None` | 空值，不能崩 |
| `券后199-299` | min=199, max=299 | 区间 |
| `￥199.00` | 199.0 | 货币符号 |

**必须写单元测试**，覆盖每一个边界情况。测试覆盖率是简历上的硬指标，也是面试官最可能追问的地方。

### ✅ 3. 可视化

| 图表 | 可行性 | 注意事项 |
|---|---|---|
| 价格分布柱状图 | ✅ 简单 | ECharts 直出，30 分钟 |
| 销量 Top20 排行 | ✅ 简单 | 横向柱状图更好看 |
| 店铺占比饼图 | ✅ 简单 | 超过 8 个分类要合并为"其他" |
| 折线趋势图 | ⚠️ | 见"漏洞 1"，需要先解决数据源 |
| **关键词词云** | ⚠️ 有坑 | 见下 |
| 表格分页 | ✅ | 后端 `limit/offset` |

**中文词云的坑**（原文没提）：

词云按空格切词，**中文必须先分词**，否则整个标题是一个词：

1. **分词**：用 `jieba`
2. **去停用词**：过滤"的、了、包邮、正品"等无意义词
3. **电商专有噪声**：过滤"旗舰店、官方、新款、正品、特价"等高频无意义词

这个处理流程本身就是一个模块，是很好的"数据清洗"素材。

---

### ✅ 4. GLM 智能分析 —— 可行且效果好

**Token 量核算**：50 个商品 × (标题 + 价格 + 销量 + 店铺名) ≈ 每个 50–80 tokens → 总计 **2500–4000 tokens**，GLM-4-Flash 上下文 128K，毫无压力。

**四个必须注意的点**：

1. **`temperature` 范围是 (0, 1)** —— 智谱的参数范围与 OpenAI 不同，传 1.5 会直接报错（你在 aiwenda 项目踩过这个坑）

2. **让它输出 JSON，而不是 Markdown**
   - ❌ "请输出一份 Markdown 报告" → 格式不可控，无法测试
   - ✅ "请按以下 JSON schema 输出" → 可控、可测试、可缓存、前端自由渲染

   ```json
   {
     "market_overview": {"price_bands": [], "main_selling_points": []},
     "pricing_strategy": {"findings": []},
     "consumer_concerns": {"top_concerns": []}
   }
   ```

3. **按数据指纹缓存，不按时间缓存**
   - 原文说"攒一批统一调一次"，方向对
   - 但更进一步：把分析结果按**输入数据的哈希**存入 `analysis_reports` 表。数据没变就命中缓存，一次 API 都不调。否则用户刷新一次页面就烧一次钱。
   - 面试话术："我用数据指纹做缓存键，而不是时间窗口 —— 因为同样的输入必须得到同样的缓存命中，否则缓存就没有意义。"

4. **模型选择**：`glm-4-flash` 免费额度足够开发全程，`glm-4-plus` 效果好但收费。开发用 flash，最终演示可切 plus。

`pandas.to_excel()` + `openpyxl`，十几行代码。注意：导出大数据量时用流式响应（`StreamingResponse`），不要把整个 DataFrame 塞内存。

### ✅ 6. 告警 —— 但"前端标记"不算告警

原文说"简单版：前端标记" —— **前端标记只是个筛选器，不是告警**。告警的定义是"用户不看着屏幕也能收到通知"。

**正确实现**：

```
后台定时任务检查价格 → 命中规则 → 写入 alerts 表 → 推送到外部渠道
```

**推送渠道建议**（按易用度排序）：

| 渠道 | 难度 | 说明 |
|---|---|---|
| **Server酱 / 企业微信机器人 / 钉钉机器人** ⭐ | ⭐ | 免费、国内直连、几行代码搞定，最适合演示 |
| 邮件 SMTP | ⭐⭐ | 容易进垃圾箱，需配置 SPF |
| Windows 桌面通知 | ⭐ | 只有本机能收到，适合本地 demo |

### ✅ 7. APScheduler 定时任务

可行。**两个坑**：

1. **默认的 `MemoryJobStore` 重启后任务全部丢失** → 用 `SQLAlchemyJobStore` 持久化，或者干脆自己写一个 `while True` + sleep 的调度循环（更可控、更好调试）
2. **必须加运行锁**：上一次采集没跑完，下一次又启动了，会导致重复采集和数据污染。用 `max_instances=1` 或数据库标志位

## 六、进阶功能的现实评估

### 图片采集 ⚠️ 有坑

**防盗链问题**：直接 `<img src="对方域名/xxx.jpg">` 大概率返回 **403**，因为服务器检查 `Referer` 头。

**替代方案**：

```
后端图片代理：/api/proxy-image?url=xxx
   └─▶ 服务端带正确的 Referer + UA 去请求
         └─▶ 转发给前端
```

或下载到本地 `data/images/`，数据库只存路径（**不要存 BLOB**）。

---

### 评论情感分析 ⚠️ 难度被严重低估

**评论是所有数据里反爬最狠的**，比商品列表难一个数量级：

- 京东 / 淘宝：评论接口需要登录态 + 签名
- SMZDM：相对松，但要翻页，且评论量有限

**替代方案**：

1. 用公开中文情感数据集（ChnSentiCorp、微博情感数据集）验证分析 pipeline
2. 只抓少量（几十条）真实评论，重点展示"清洗 → GLM 分析 → 结构化输出"的**流程完整性**

面试话术："数据源受限于合规和反爬，我用公开数据集验证了 pipeline 的效果，重点在于 prompt 设计和结果结构化。"

## 七、架构建议

```
ecom-intel/
├── backend/              # FastAPI 应用
│   ├── main.py
│   ├── api/              # 路由层
│   ├── db/               # SQLAlchemy 模型 + 会话管理
│   └── services/         # 业务逻辑
├── scraper/              # 采集层（可独立运行）
│   ├── sources/          # 每个站点一个 adapter（smzdm.py / mock.py）
│   ├── pipeline/         # 清洗、去重、增量判断
│   └── worker.py         # 独立 worker 进程
├── analysis/             # GLM 分析
│   ├── prompts/          # prompt 模板
│   └── reporter.py       # 报告生成 + 缓存
├── frontend/             # 静态页 / Vue
├── data/                 # SQLite + 图片
│   └── images/
├── tests/                # 单元测试（清洗函数必须覆盖）
└── docs/
```

**关键设计原则：采集层独立于 Web 层。**

- 采集器可以 `python -m scraper.worker` 单独跑（调试方便）
- 也可以被 API 触发（入队）
- **这个解耦是面试重点** —— 说明你懂"关注点分离"

## 十二、真实数据标定实录（开工后的实测发现）

> 本节记录的是**计划付诸实施后**、在真实 SMZDM 页面上实测到的情况。
> 与前十节（纸上评估）不同，这一节的每个数字都来自实际抓下来的数据。
>
> 保留这一节的原因：**它是本项目最有说服力的面试素材**——
> 因为它展示的不是"我用了什么技术"，而是"我用数据推翻了自己的设计"。

### 12.1 采集侧：WAF 升级与主动停手

`/jingxuan/` 前 5 页抓取正常（HTTP 200、服务端渲染、结构完整），但在累计约
50–100 次请求后，服务端行为发生变化：

| 阶段 | 现象 |
|---|---|
| 正常期 | HTTP 200，约 380 KB 完整 HTML，可正常解析 |
| 升级期 | HTTP 200，**但响应体只有 1681 字节**，内容是腾讯验证码（TCaptcha）的 JS 挑战页 |
| 拦截期 | 全部端点 **HTTP 403** |

响应体里的特征字符串（`seqid` 变量、`TCaptcha.js` 引用）确认了这是
**WAF 的验证码挑战**，而不是页面改版或网络故障。

**处理方式：立即停止对 SMZDM 的请求，不做任何绕过尝试。**

理由有两层：

1. **合规层**：绕过验证码是明确越界的行为。本项目的定位是"学习研究用途的
   数据管道演示"，不是"突破访问控制"。这条线一旦跨过，项目性质就变了。
2. **工程层**：即便绕过成功，**这正是"采集层不可靠"的最好证据**——
   把系统建立在一个随时会被封的通道上，本身就是设计缺陷。
   正确的应对是让系统在**没有实时采集**的情况下仍然完整可用。

**由此产生的设计决策：离线夹具回放。**

把已验证的 HTML 落盘到 `spike/_raw/`（10.3 MB，26 个文件），
标定脚本默认离线运行，需要联网时才显式加 `--fetch`：

```python
OFFLINE = "--fetch" not in sys.argv
```

这不是权宜之计，而是一个正经的工程模式：
**测试和标定不应该依赖外部服务的可用性**。CI 里跑不了的东西不算测试。

### 12.2 数据源侧：双源策略

| 端点 | 实测结果 | 用途 |
|---|---|---|
| `search.smzdm.com` | HTTP 202 + `X-WAF-UUID` | ❌ 不可用 |
| `/fenlei/3cjiadian` | robots.txt **明确禁止** | ❌ 不抓 |
| `/fenlei/<其他 slug>` | HTTP 200 | ✅ 品类覆盖 |
| `/jingxuan/` | HTTP 200，服务端渲染 | ✅ 管道验证 |

**两个必须记下来的坑：**

1. **`/fenlei/` 的 slug 不是可靠的品类过滤器。** 实测三个不同 slug 返回的
   商品集合**字节级相同**——说明该路径的参数对内容没有实际约束力。
   不能据此声称"按品类精确采集"。
2. **`/fenlei/` 分页无效。** 翻页返回同一批内容。所以品类覆盖只能靠
   多个 slug 分别抓一次，不能靠翻页深化。

**最终策略**：`/jingxuan/` 用于**管道验证**（分页、时间戳、事件归并语义），
`/fenlei/<slug>` 用于**品类覆盖**（约 100 条配件商品）。两个来源在库中
用 `source_channel` 字段区分——因为两条通道的**记录时间语义不同**
（精选页的 `timesort` 是爆料发布时间，类目页没有这个语义）。

### 12.3 清洗侧：真实价格格式的分布

从真实页面提取的 543 个价格样本，格式分布如下：

| 格式 | 出现次数 | 说明 |
|---|---|---|
| `N元` | 217 | 普通价格 |
| `N元（需用券）` | 171 | 券后价 |
| `暂无报价` | 67 | 脏数据 → `(None, None)` |
| `N元起` | 50 | 开区间 → `(N, None)` |
| `N元（需买N件，需用券）` | 20 | **件数干扰** |
| `N元（淘金币可抵N元起）` | 17 | **抵扣额干扰** |
| `评论打卡瓜分N万积分！` | 1 | **促销 banner 文本，不是价格** |

**三个"第二个数字"陷阱**（这一条最有价值，因为朴素实现会全部中招）：

| 输入 | 朴素实现的结果 | 正确结果 |
|---|---|---|
| `193元（淘金币可抵0.97元起）` | `(0.97, None)` —— 取 min 或"元起"规则 | `(193, 193)` |
| `18.5元（需买3件，共55.5元）` | `55.5` —— 取最后一个数字，**虚高 3 倍** | `(18.5, 18.5)` |
| `8.01元（需买2件，需用券）` | `2` —— 取最小数字 | `(8.01, 8.01)` |

**结论：价格 = 第一个「数字+元」，而不是最大/最小/最后一个数字。**
括号里的内容全是**成交条件**，不是价格本身。

这条规则最终被实现为**优先级分流**（带单位区间 → 第一个"数字+元" →
裸区间 → 货币符号），并有 5 个真实用例守护（`test_parse_price_multi_number_traps`）。

### 12.4 ★ 归并阈值标定：一次被数据推翻的设计

**这是本节的核心，也是整个项目最有价值的工程决策。**

#### 背景

把 `/jingxuan/` 抓来的东西存进库后，会撞上一个语义问题：
**抓到的每一条不是"商品"，而是"爆料"（价格事件）。**
同一商品被反复爆料会产生多条记录，而"价格趋势图"需要的是每个商品的
价格时间序列。

所以需要一个**事件归并**逻辑：新爆料进来时，判断它属于哪个已有商品。

原始设计是两层：

```
硬门槛（品牌 + 规格 token） ── 一票否决
     ↓ 通过
软门槛（Dice ≥ 0.75）      ── 判定是否同一商品
```

**软门槛负责"判定"这个定位，是错的。** 下面是推翻它的过程。

#### 方法

1. 抓取真实标题，去重后得到 **277 条**（其中 51 条属于数码配件品类）
2. 消除**所有**先验假设，纯粹用数据说话
3. 人工逐对标注：**11 对**标题，判定"是不是同一款商品（SKU 层面）"
4. 计算三种相似度指标，看真阳性和假阳性能否被分开

> ★ **方法上的一个自我纠正**：第一版标注脚本用**模糊匹配**把标注文本
> 映射到语料标题，结果选错了标题，算出的分数和手算对不上。
> 改成**精确锚定**（命中 0 条或 1 条以上直接报错退出）后才得到可信结论。
> **测试脚手架自己出错比没有测试更危险**——它会给出错误的安全感。

#### 结果：三种指标全部不可分

| 标签 | 包含度 | Dice | Jaccard | 标题对 |
|---|---|---|---|---|
| 同款 | 0.750 | 0.545 | 0.375 | `FreeClip 2 …冰莓紫 Type-C` / `FreeClip 2 耳夹式耳机` |
| 同款 | 0.800 | 0.667 | 0.500 | `FreeClip 2 …Type-C` / `freeclip2 …冰莓紫` |
| 同款 | 0.667 | 0.533 | 0.364 | `Pura X Max 12GB+256GB` / `HUAWEI 华为 Pura X Max 手机` |
| 同款 | 1.000 | 1.000 | 1.000 | `百亿补贴：酷态科 充电宝10号…` / `酷态科 充电宝10号…` |
| **不同** | **0.857** | **0.706** | 0.545 | `iPhone 18 Pro Max …256GB` / `iPhone 18 Pro` |
| **不同** | **0.833** | **0.769** | **0.625** | `iPhone 18 Pro` / `iPhone Duo` |
| 不同 | 0.500 | 0.500 | 0.333 | `FreeClip 2` / `FreeClip 开放式设计`（一代） |
| 不同 | 0.500 | 0.400 | 0.250 | `酷态科 10号` / `酷态科 CP13` |
| 不同 | 0.500 | 0.444 | 0.286 | `斯凯奇 …女士跑鞋` / `斯凯奇 …男士健步鞋` |
| 不同 | 0.500 | 0.500 | 0.333 | `米良品 拖轮购物车` / `米良品 掏耳神器` |

**汇总判定：**

| 指标 | 真阳性最低 | 假阳性最高 | 结论 |
|---|---|---|---|
| 包含度 | 0.667 | **0.857** | ❌ 不可分 |
| Dice | 0.533 | **0.769** | ❌ 不可分 |
| Jaccard | 0.364 | **0.625** | ❌ 不可分 |

**三种指标全部不可分。** 任何单一阈值都无法同时收下全部真阳性、
排除全部假阳性。

最致命的是这一对：

```
Apple 苹果 iPhone 18 Pro 5G手机    ← 不同商品
Apple 苹果 iPhone Duo 5G手机       ← Dice 0.769 / 包含度 0.833
```

它的分数**高过四个真阳性中的三个**。如果归并决策交给相似度阈值，
这一对必然被错误合并，于是 `iPhone 18 Pro` 的价格序列里混进了
`iPhone Duo` 的价格——**而且不会报错，分析结论静默失真**。

> 直观原因：中文电商短标题清洗后通常只有 **4–7 个 token**，
> 在这个量级上，集合指标的取值是**离散且跳跃的**——
> 差一个词就从 1.0 掉到 0.5。信息量不足以支撑"同一商品判定"这么细的任务。

#### 转折：真正干活的不是相似度

回头审视那对最危险的假阳性，发现它有个特征：

| 标题 | 型号 token |
|---|---|
| `iPhone 18 Pro` | `{18, pro}` |
| `iPhone Duo` | `{duo}` |

**不相等。** 而所有真阳性对的型号 token 都是相等的：

| 标题对 | 型号 token |
|---|---|
| `FreeClip 2 …` / `FreeClip 2 …` | `{2}` / `{2}` ✅ |
| `freeclip2` / `FreeClip 2` | `{2}` / `{2}` ✅（修复后） |
| `酷态科 10号` / `酷态科 10号` | `{10, 10000毫安}` / 同 ✅ |
| `iPhone 18 Pro` / `iPhone Duo` | `{18, pro}` / `{duo}` ❌ 拦下 |
| `酷态科 10号` / `酷态科 CP13` | `{10}` / `{13}` ❌ 拦下 |
| `FreeClip 2` / `FreeClip`(一代) | `{2}` / `{}` ❌ 拦下 |

**型号 token 相等是必要条件，而相似度不是。**

#### 修正后的设计

```
新爆料
  └─▶ 归一化（去促销噪声、字母数字边界切分、★保留规格 token）
        └─▶ 【第一层 确定性规则】负责【排除】，不负责确认
              · 品牌必须相容（提取不出 → 视为通过，"无证据不否决"）
              · 型号 token 必须【严格相等】
              ├─ 不相等 → 绝不自动合并
              │    └─ 但若包含度 ≥ 0.75 → 标记待人工核对（不是静默丢弃）
              └─ 相等 → 进入第二层
                    └─▶ 【第二层 相似度确认】只负责【确认】
                          · 包含度 = |A∩B| / min(|A|,|B|)
                          ├─ ≥ 0.75        → 自动归并
                          ├─ 0.50 ~ 0.75   → 新建 + 标记 suspected_duplicate_of
                          └─ < 0.50        → 新建，不标记
```

**两层的分工是有讲究的**：
确定性规则可以证明"**不是同一个**"，但证明不了"是同一个"
（品牌型号都对也可能只是同系列）；相似度可以提示"**可能是同一个**"，
但不足以单独下结论。让两者各做擅长的事。

#### 修正后的效果（同一批 11 对标注）

| 指标 | 值 |
|---|---|
| 真阳性 TP | 3（正确归并） |
| 真阴性 TN | 7（正确分开） |
| **假阳性 FP** | **0**（零错归并） |
| 假阴性 FN | 1（漏归并，且被标记） |

**加上硬门槛后，通过门槛的 5 对里：需要拒绝的最高 0.500，
需要接受的最低 0.750 → 阈值区间 `[0.500, 0.750]`，完全可分。**

```
★ 核心结论：三种相似度指标全部不可分，加上类型门槛立刻可分
指标          真阳性最低   假阳性最高
包含度            0.667      0.857   ★ 不可分 ❌
Dice             0.533      0.769   ★ 不可分 ❌
Jaccard          0.364      0.625   ★ 不可分 ❌
--- 加上硬门槛后（只看通过型号门槛的 5 对）---
包含度            0.750      0.500   可分 ✅
```

#### 标定过程中额外发现的两个真 bug

| 现象 | 根因 | 修复 |
|---|---|---|
| `FreeClip 2`（带空格）与 `freeclip2`（不带）被判为不同商品 | 型号 token 分别是 `{2}` 和 `{freeclip2}` | 归一化时在**字母数字边界插入空格**（`freeclip2` → `freeclip 2`） |
| `iPhone 18 Pro` 与 `iPhone 18 Pro Max` 型号集相同 | `Pro`/`Max` 是纯字母，"提取含数字的 token"这条朴素规则抓不到 | 增加**型号后缀词表**（`pro`/`max`/`plus`/`ultra`/`青春版`…） |

两个 bug 都是**用真实数据标定才暴露的**——自己编测试用例时，
只会想到自己知道的情况。

#### 主动接受的代价

严格相等会**漏掉**"长标题带规格 vs 短标题不带规格"的同款，例如：

```
华为 Pura X Max 12GB+256GB 橄榄金…   型号 token {max, 12, gb, 256}
HUAWEI 华为 Pura X Max 手机          型号 token {max}
                                 → 不相等 → 漏归并
```

标定中试过放宽成"一个是另一个的子集"，结果 `iPhone 18 Pro`
`{18, pro}` 与 `iPhone 18 Pro Max …256GB` `{18, pro, max, 256, gb}`
会被判为相容——**但它们是两个 SKU**。

**这个代价是主动接受的**：

- 漏归并 → 只是少几个价格点，且会被标记进人工核对队列，**可恢复**
- 错归并 → 价格序列里混进别的商品的价格，**静默失真，不可发现**

两害相权，取保守的那个。这条取舍被写进了
`tests/test_dedup.py::test_known_cost_of_strict_equality`，
不允许后来者"优化"掉而不自知。

#### 局限的诚实说明

- 标注集只有 11 对。样本量小，阈值 `[0.500, 0.750]` 的区间宽度是**测出来的**
  而不是**推导出来的**，真实生产中应随采集天数增加再校准一次。
- 单次快照里"同一商品被多次爆料"的正样本天然稀少（**这正是要解决的问题本身**），
  所以正样本主要来自"规格相同、措辞不同"的标题对。
  真实生产中正样本会随采集天数累积变多。
- 11 对里有 2 对是"通过门槛但落进灰色地带"的假阳性
  （斯凯奇、米良品），它们会被标记但不会被合并——
  **灰色地带的精确率约 33%**。这是可接受的：核对队列本来就该以召回为先，
  代价只是人扫一眼。

这些局限如实写在这里，不假装标定是完美的。

### 12.5 这一节的复用价值

这套标定方法可以直接迁移到任何"短文本实体归并"场景
（商品去重、新闻事件聚合、工单合并）。它的核心不是某项技术，而是三条原则：

1. **先用数据验证指标本身，再谈阈值。** 我们花了半天证明"三种常用相似度
   指标在这个数据上不可分"，这半天的价值高于调参一周——
   因为它避免了把系统建立在一个**根本无效的信号**上。
2. **确定性规则负责排除，概率信号负责确认，不要反过来。**
   反过来用的后果是"看起来相似但确实不同"的样本被静默吞掉。
3. **把取舍和代价写进测试。** 漏归并是可接受的、错归并不是——
   这个判断必须固化成 `test_never_merges_dangerous_pairs`，
   否则下一个改代码的人（包括三个月后的自己）会把它"优化"掉。

## 十三、Mock 数据生成的三个实测发现

第十二节记的是**真实数据**上的标定。这一节记的是**合成数据**上的踩坑，
两者是不同性质的工作，但教训同源：**统计指标正常 ≠ 数据是对的**。

### 13.1 本文档第 107 行的建议是错的：不能用随机游走

第 107 行（早期方案）写的是：

> 按真实价格分布规律（**随机游走** + 促销跳变）生成过去 90 天的价格序列

实现时照着写成了 `p[t] = p[t-1] * (1 + ε)`，日波动 σ=0.012。
**实测 90 天后价格中位数跌到初始值的 12%**——折线图是一条一路下滑的滑梯。

原因是乘性误差会累积：`(1+ε)` 连乘 90 次，其对数是一个方差随时间线性增长的
随机游走，于是价格在对数空间里"走远了"。

正确做法：**所有价格围绕一个固定的 base 波动**，绝不围绕前一天累乘。

```python
错： p[t] = p[t-1] * (1 + ε)      # 对数漂移
对： p[t] = base   * (1 + ε)      # 永远在 base 附近，促销后自然回归
```

> **面试可讲**：这条建议是我自己写的方案文档里的，实现时才发现是错的。
> 更值得讲的是**判别方式**——所有统计指标（中位数、量级、无负值）当时都是"正常"的，
> 是画成图一眼看出来的。所以我后来把"画图"从"演示素材"改成了
> **开发期自检工具**，`spike/plot_seed.py` 的三张图和测试是同等地位的东西。

> 补充一点：直觉上会去断言"末价/首价的**均值**≈1"来判断有没有漂移。
> 这条对两种实现**都成立**——随机游走在对数空间近似对称，N 条路径的均值照样是 1，
> 只是每条路径各走各的。真正的判别式是**离散度**：
> 正确实现下 80 条序列的中位数 max/min < 1.1，累乘实现会到几倍。
> 见 `tests/test_seed.py::test_no_compounding_drift`。

### 13.2 大促日会被普通促销"吃掉"（而测试一直是绿的）

设计意图：第 30 天和第 75 天是全品类大促（模拟 618 / 双11），
让阶段③ 的 GLM 能检出"这两天有全品类价格低谷"——这是给 AI 出的考卷，
答得出来才说明它真在读数据。

原实现把大促判定写在了 `if promo_left == 0:` **内部**：

```python
if promo_left == 0:                    # ← 普通促销进行中时，整个分支不执行
    if t in BIG_PROMO_DAYS:            # ← 大促被跳过
        ...
```

于是当第 30 天正好落在一次普通促销中间（概率约 17%）时，大促**根本不发生**。
两个大促日合计，约 **30% 的商品缺至少一个大促**。

★ 关键在于：**有一个测试一直在跑，而且一直通过**。
它断言的是"200 个商品的日均值在大促日更低"——70% 的商品是对的，
取平均就把 30% 的缺失抹平了。

是价格曲线图暴露的：图上有几个商品第 30 天压根没有低谷。

修法：大促判断移到 `promo_left == 0` 之外，**无条件覆盖**正在进行的促销
（现实里也确实是这个语义——618 开始，日常促销就被盖掉了）。

> **面试可讲**：这是"**聚合指标掩盖个体差异**"的教科书案例。
> 凡是设计意图里带**全称量词**的（"全品类""每个商品都""所有接口"），
> 断言就必须落在个体上，不能落在均值上。
> 补强的 `test_every_single_product_has_the_big_promo` 是逐商品检查的，
> 修复前报出 7/240 缺失。

### 13.3 图会骗人：15 字截断让三个不同 SKU 看起来像"同一商品记了三次"

销量 Top20 图上出现了三条看起来一模一样的条形：

```
绿联 磁吸手机指环扣 金属 …     45,794
绿联 磁吸手机指环扣 金属 …      7,595
绿联 磁吸手机指环扣 金属 …      7,022
```

第一反应是"数据严重错误：同一个商品被记了三次，销量还不一样"。
查库才发现 Top20 里 **19 个标题都是唯一的**——那三条是**不同颜色的 SKU**
（深空灰 / 黑色 / 白色），而颜色恰好是标题的最后两个字，被 `t[:14]` 切掉了。

**数据没错，是图在骗人。** 按字符数截断对中文天然不公平：
15 个中文字占的宽度约为 15 个英文字母的 1.8 倍；
而"数码配件"品类的标题恰好是「品牌中文 + 型号英文 + 规格 + 颜色」，
最需要保留的颜色和规格都在尾部。

修法：按**显示宽度**截断（中文算 2、ASCII 算 1），
见 `spike/plot_seed.py::elide`。

> **面试可讲**：我先怀疑数据，查完才确认是呈现层的问题。
> 这个顺序是对的——但值得说出来的是**查证过程本身**：
> 发现"三个一样的标题销量差 6 倍"时，第一反应应该是去数据库核对，
> 而不是直接改图。如果反过来（先改图让它"好看点"），
> 就正好掩盖了一个可能真实存在的数据 bug。

### 13.4 三个发现共同的方法论

| 发现 | 统计指标 | 谁发现的 | 根因 |
|---|---|---|---|
| 累乘漂移 | 全部"正常" | 价格曲线图 | 对数随机游走 |
| 大促被跳过 | 均值断言通过 | 价格曲线图 | 分支嵌套位置错误 |
| 标签截断 | 数据本身没问题 | 看图起疑 → 查库 | 中英文宽度不等 |

三次都是**先看图**。所以 `docs/charts/` 里的三张图不是 README 的装饰，
而是和 `pytest` 并列的验证手段——这也是为什么 matplotlib 被列进
`requirements.txt` 的**硬依赖**而不是 dev 依赖。

## 十四、API 层的四个实测发现（阶段 2）

阶段 2 写完了 6 个统计接口 + 2 个商品接口，配套 69 个新测试
（`test_textutil.py` 26 个 + `test_api_smoke.py` 43 个），全库 281 个测试全绿。

这一节记录的是**测试和机械验证抓出来的四个问题**——
其中三个是代码 bug，第四个推翻了我自己在阶段 1 写下的一个"修复"。

### 14.1 空状态契约：同一个判断，写了两遍，漏了一遍

这个项目的 API 有一条自我约束：**「空」和「错」是两件事，而且空必须解释自己为什么空**。
`?source=smzdm` 下销量图没有数据，这不是 404、不是 500，
而是 200 + 空数组 + 一句"真实电商不公开销量"。

问题出在**有两条不同的空**：

| 情况 | 正确的话 |
|---|---|
| 这个数据源一条商品都没有 | "该数据源暂无数据（尚未采集）" |
| 有商品，但这个数据源没有销量字段 | "该数据源不提供销量数据（真实电商不公开）" |

第一版我把这个判断写在了 `overview()` 里，写对了。
`sales_top()` 里只检查了"有没有销量"，于是 **`?source=smzdm` 走进来会得到第二句话——
而那个数据源其实一条商品都没有**。测试 `test_empty_source_says_there_is_no_data_not_no_sales`
把它抓了出来。

修法不是再抄一遍判断，而是抽成 `_empty_notice(product_count)`：

```python
def _empty_notice(product_count: int) -> str:
    return SALES_UNAVAILABLE_NOTICE if product_count > 0 else NO_DATA_NOTICE
```

> **面试可讲**：这条规则我在两个地方实现了两遍，漏了一处。
> 真正该记住的不是"要小心别漏"，而是**同一个判断出现第二次时就该抽出来**——
> 漏掉的地方永远不会是自己以为写全了的那个。

同一类问题还有一个更隐蔽的版本：`PriceDistributionOut` **压根没有 `notice` 字段**。
前四个接口我都记得加，唯独价格分布忘了——它的空响应是 `buckets: []` 且没有任何解释，
前端只能显示"暂无数据"，**而"为什么没有"这个信息在接口层就丢了**。
补字段的时候我顺手加了一条测试：**一次性遍历全部五个空响应接口**，
断言每一个都带了非空的 `notice`。漏掉第六个接口的可能性依然存在，
但至少新增接口时会被这条测试拦住。

### 14.2 `elide_middle` 的差一错误（budget=2）

截断函数在预算极小的时候会返回 `'a…a'`——**显示宽度 3，超过预算 2**。
原因是 `max(1, ...)` 给头和尾各保底 1 个单位，再加上省略号本身就 3 了。

参数化测试 `test_result_never_exceeds_budget` 覆盖了 2/3/4/5/10/20/26/40 各档，
只有 budget=2 炸。修法是加一个早退分支：**尾巴拿走全部预算**。

```python
if avail < 2:
    return "…" + _take_tail(text, avail)
```

同一轮里还有第二个顺序问题：**"放得下就原样返回"的判断必须排在预算守卫之前**，
否则 `budget <= 0` 的早退会先把正常输入也一起吃掉。

> **面试可讲**：这个 bug 之所以能被抓到，是因为**测试是参数化的而不是举了几个例子**。
> 我手写用例的话会写 budget=20、budget=26，绝不会写 budget=2——
> 而边界恰恰只在参数空间的角落上。

### 14.3 ★ 证伪：`title_short` 那个"修复"根本不成立

这是本阶段最有价值的一个发现，因为**它推翻的是我自己在阶段 1 留下的结论**。

背景见 §13.3：销量 Top20 图里三个不同颜色的 SKU 看起来像同一个商品，
因为按字符数截断把标题尾部的颜色切掉了。阶段 1 的修法是
**改成按显示宽度截断，并且保留尾部**（中文算 2、ASCII 算 1，头部 60% + 尾部 40%）。

阶段 2 把这段逻辑搬进 `app/textutil.py` 并补测试时，我写了一条测试：

> 三个只差颜色的 SKU，截断后必须仍然长得不一样。

**它没过。**

我以为是预算选小了，于是把阈值从 26 调到 30、再到 40，逐个实测：

| 预算 | 三个 SKU 的 `title_short` | 可区分？ |
|---|---|---|
| 26 | 三个完全相同 | ❌ |
| 30 | 三个完全相同 | ❌ |
| 40 | 三个完全相同 | ❌ |
| 60 | 三个都是完整原文，彼此不同 | ✅ |

去看那条标题的实际结构才明白：

```
绿联 磁吸手机指环扣 金属 超薄 深空灰 商务款 送礼佳品
```

颜色（`深空灰`）在**第 5 个 token**，后面**还跟着 2 个纯营销 token**。
"保留尾部"保留下来的是"商务款 送礼佳品"——**恰好是信息量为零的那部分**。
预算 60 之所以"能区分"，是因为 60 已经大于标题本身，等于没截断。

结论不是"把预算调到 60"，而是：**任何固定的截断策略都无法保证不同 SKU 一定长得不一样。**
保留尾部在颜色靠后时有用，在颜色靠前、营销语靠后时就是有害的；
调大预算只是让它退化成"不截断"，那图例就放不下了。

**真正的修法是换一层解决：图例只负责放得下，完整标题交给 tooltip。**
`app/textutil.py` 的模块 docstring 现在写着这张实测表格和上面那句结论；
`charts.js` 的 `renderSalesTop` 在 tooltip 的 formatter 里用的是完整 `it.title`。

对应的测试也从一条改成了两条：
一条断言"工具提示必须拿到完整标题"（这是真正要保证的契约），
另一条断言"截断在预算内且带省略号"（这是排版约束），
**而"不同 SKU 必须可区分"这条被我删掉了——因为它做不到，留着就是一条假承诺。**

> **面试可讲**：这条最有价值的地方是**测试推翻了我自己的修复**。
> 阶段 1 我以为"改成按宽度截断 + 保留尾部"就解决了，
> 阶段 2 补测试时才发现它只是把问题从"颜色被切掉"变成了"颜色被营销语顶掉"。
>
> 而且这里有个陷阱：**如果我把预算直接调到 60，测试会变绿**，
> 然后我会以为自己修好了——实际上只是绕开了。
> 所以值得说的是那个"我准备调参数，先停下来量了一下"的动作：
> 量完发现**26/30/40 三个档位的结果一模一样**，
> 那就说明这不是"调得不够大"，而是**策略本身不对**。

### 14.4 一个被自己写错的断言：25 是合法的分桶步长

价格分布的分桶用的是"好看的步长阶梯"：
`(5, 10, 20, 25, 50, 100, 200, 250, 500, 1000, 2000, 2500, 5000)`。

测试里我写的是 `assert step % 10 == 0`，结果真实数据算出来的步长是 **25**，测试红了。

**是我测试写错了**：25 就在我自己列的阶梯里，是我写断言时想当然地
把"好看的步长"理解成了"10 的倍数"。

改成 `assert step in GOOD_STEPS` ——**断言应该检查它真正依赖的那个性质**，
而不是一个碰巧在多数情况下等价的近似。

> **面试可讲**：这个错误很小，但它和 §14.1 是同一类：
> **规则应该只有一处定义**。步长阶梯是个常量元组，
> 断言却不引用它、而是重新描述了一遍"什么算好步长"，
> 于是两份描述对不上时，我第一个怀疑的是代码而不是测试。

### 14.5 四个发现的方法论

| 发现 | 抓它的手段 | 根因 | 性质 |
|---|---|---|---|
| 空状态文案用错 | 单测（分阶段灌数据） | 同一判断写了两遍 | 代码 bug |
| `PriceDistributionOut` 缺 `notice` | 单测（遍历全部接口） | 规则覆盖不全 | 代码 bug |
| `elide_middle` 超预算 | 参数化单测 | 边界差一 | 代码 bug |
| `title_short` 策略不成立 | 单测 → 实测标定 | **假设错了** | 设计缺陷 |
| 步长断言过严 | 单测 | 规则描述了两遍 | 测试 bug |

前三条是"代码没实现好"，第四条是"想法本身不对"，第五条是"检查方式不对"。
四者混在一起时最容易的反应是**全都当代码 bug 改**——
而第四条那样改，只会把问题藏起来。

### 14.6 一条没能验证的验证点（如实记录）

### 15.1 ★ 同一套 key 规则写了三遍，两份已经分叉

"GLM key 配好了没有"这个问题，项目里有三条判断路径：`main.py` 的健康检查、
`glm_client.key_configured()`、以及分析接口实际调模型那一刻的检查。
三处都是同一套三查：**空 / 非 ASCII / 占位符**。

看起来是一致的。但把它们逐字抄出来并排跑，结果是这样（下表是本机实测，不是推测）：

| 探测值 | `main.py`（旧） | `glm_client`（新） | 一致？ |
|---|---|---|---|
| `your_key_here` | False | False | ✓ |
| `your-api-key` | False | False | ✓ |
| `changeme` | False | False | ✓ |
| `xxx` | False | False | ✓ |
| `sk-xxx` | False | False | ✓ |
| **`replace_me_please`** | **True** | **False** | **★ 分叉** |
| **`example-key-123`** | **True** | **False** | **★ 分叉** |
| **`xxxxxx`** | **True** | **False** | **★ 分叉** |
| **`TODO_KEY`** | **True** | **False** | **★ 分叉** |
| `abc123def456ghi789` | True | True | ✓ |
| `请填入你的key` | False | False | ✓ |

根因很小：`main.py` 里是 `key.lower() not in {"your_key_here", ...}`（**精确相等**），
而 `glm_client.py` 里是 `any(mark in lowered for mark in _KEY_PLACEHOLDER_MARKS)`
（**子串包含**，且清单里多了 `replace` / `example` / `todo`）。
两份清单看着"差不多"，语义却是两回事。

**但真正要记的是第 2~5 行**：五个值里，阶段 2 已经存在的那条冒烟测试用的**恰好是
`your_key_here`**——而它是**两边一致的**。所以这条分叉从阶段 2 起就在代码里，
测试一直是绿的。**不是测试没跑，是测试探查的正好是一致的那一点。**

后果不是"少拦了一个占位符"，而是**两个接口互相矛盾**：

```
/api/health   → llm_configured: true  → 前端把「生成分析报告」按钮点亮
用户点下去     → analysis 接口抛 503 "GLM_API_KEY 未配置"
```

修法是把 `main.py` 里那份实现删掉，改成 `from app.analysis.glm_client import key_configured`。
**并且补了一条测试**（`test_the_same_rule_governs_health_and_the_analysis_endpoint`），
它断言的不是"某个端点返回了什么"，而是**两个端点之间的关系**：

```python
# 对 8 个探测值，逐一断言：健康检查说可用 ⟺ 分析接口不会返回 503
assert healthy == (status != 503)
```

最后我**验证了这条测试真的能抓到问题**：把旧规则 monkeypatch 回 `main.py`，
四个分叉值全部报红。

> **面试可讲**：这条最有价值的地方是"为什么它一直没被发现"。
> 一份规则写了三遍，而**已有的测试只探查了它们恰好一致的那一点**——
> 所以"有测试"和"测试覆盖了这个规则"是两件事。
>
> 修法也不是"把两处改成一样"，而是**删掉一份**：只要第二份还存在，
> 它迟早会在某个新占位符上再次分叉。断言两个接口的**关系**而不是各自的值，
> 也是同一个道理——检查"它们是否一致"比检查"它们是否等于我期望的值"更能防住未来的分叉。

### 15.2 ★ `CreatedAt` 从字段名黑名单里穿了过去

`fingerprint.py` 里有一道运行时兜底 `_assert_fingerprint_safe()`，
拦的是"把会变、但不影响结论的字段算进指纹"——自增 id、`created_at`、`last_crawled_at` 这类。
实现是字段名黑名单：

```python
_FORBIDDEN_KEYS = frozenset({"id", "created_at", "updated_at", "last_crawled_at", ...})
...
if key.lower() in _FORBIDDEN_KEYS:   # ← 旧写法
    raise ValueError(...)
```

`key.lower()` 看起来已经把"大小写不敏感"处理掉了，模块注释里也这么写着。
但我写了一条测试去问"**这个兜底真的兜住了吗**"，拿 `CreatedAt` 试了一下：

**没拦住。**

原因：`lower()` 只规范**大小写**，不规范围**分隔符**。`createdAt` 压不成 `created_at`——
而**任何从 JS / JSON 系统抄过来的字段名都是 `createdAt` 这个形状**，
也就是说这道兜底对最常见的那一类命名约定恰好完全失效。

修法是加一个 `_key_shape()`，把字段名压成只剩字母数字再比对：

```python
def _key_shape(key: str) -> str:
    """`created_at` / `createdAt` / `created-at` / `created at` → 全部是 `createdat`"""
    return "".join(ch for ch in key.lower() if ch.isalnum() and ch.isascii())
```

**但这里有个更重要的决定：用它做"压平后完全相等"，而不是做子串匹配。**
子串匹配看起来更保险（能拦住 `createdAtXxx` 这种变体），
代价是会**误伤 `source_id`、`shop_id`、`valid`、`candidate` 这些名字里含 `id` 的合法字段**——
而这道兜底的设计是**抛异常**，误伤的后果不是"少缓存一次"，是**分析接口直接 500**。

所以取舍写死在代码注释里：**宁可漏掉一个变体，不能把合法字段打成崩溃。**

> **面试可讲**：这个函数的 docstring 第一句是"**这个函数是被测试逼出来的**"。
> 我原本以为 `lower()` 已经解决了大小写、也就解决了"同形字段名"，
> 而实际上它只解决了问题的一半——**大小写和分隔符是两个维度**。
> 这种"看起来处理了、其实只处理了一个维度"的兜底，比没有兜底更危险，
> 因为它的注释在向读者保证它是全的。

### 15.3 ★ 一次假绿：UPSERT 绕过了 ORM 的身份映射

这一条是本节最值得讲的一个。

`force=1` 的语义是"跳过缓存、强制重新分析"。计划里明确要求：
**生成后要 `UPDATE` 覆盖同 fingerprint 的旧记录，不是 `INSERT`**——
否则会撞 `fingerprint` 的唯一索引。于是实现用了 SQLAlchemy 的
`insert().on_conflict_do_update()`，测试也照计划写了：

> 断言 ① `force=1` 后内容变新了；② 行数仍然只有 1 行；③ `id` 没变。

写完是**全绿的**。直到我怀疑其中一条断言，把两条都重新推敲了一遍，才发现：

- **① 是假红**——`content_json` 看起来"没变"，我以为 UPSERT 没生效
- **③ 是假绿**——`id == old_id` 平凡成立，因为它**就是同一个对象**

根因是两件事叠在一起：`insert().on_conflict_do_update()` 是 **Core 层语句，绕过 ORM 的身份映射**；
而 session 配了 `expire_on_commit=False`。于是 commit 之后再查，
拿回来的是**身份映射里那个旧对象**，根本没有真正从库里重新读。

修法是把读取抽成 `_rows_from_db()`，里面先 `db.expunge_all()` 清空身份映射再查。

**这里必须说清楚一件事：这是测试替身产生的假象，不是产品缺陷。**
生产环境每个请求一个全新 session，那个"旧对象"根本不存在。

但测试仍然必须消除它，因为**假绿比假红危险**：
假红会被追到底，假绿会一路留到面试现场——那时候如果被问"你怎么证明 force 覆盖了旧行"，
拿出这条测试，它证明不了任何事。

> **面试可讲**：这条的关键不是"UPSERT 要 expunge"这个技巧，
> 而是**"测试是绿的"和"测试证明了它想证明的东西"是两件事**。
> 一个断言可以在**完全没读到数据库**的情况下通过，
> 而它看起来和一条真断言毫无区别——都是 `assert a == b`，都打了勾。
>
> 我现在会问自己一句：**"如果我把被测代码改坏，这条断言会红吗？"**
> §15.1 里"把旧规则 monkeypatch 回去"验证测试能抓到，就是同一个动作。

### 15.4 文档字符串和代码说的是反话

`AnalysisOut.tokens_used` 的 docstring 我写的是"缓存命中时是 `None`"。
实测输出是 **`100`**——缓存命中时它保留了当初那次生成消耗的 token 数。

**代码是对的，文档是错的。** 这两个字段各自回答一个不同的问题：

| 字段 | 回答的问题 | 缓存命中时 |
|---|---|---|
| `tokens_used` | **这份报告**花了多少 token | 当初那个数字（不变） |
| `from_cache` | **本次请求**有没有花钱 | `true` |

如果按文档改成 `None`，前端就只能显示"—（本次没有调用模型）"，
**而用户真正想知道的是"这份报告当初花了多少"**。改的是文档，不是代码。

> **面试可讲**：文档和代码矛盾，**比没有文档更糟**。
> 没有文档时人会去读代码；有一份说反话的文档时，人会相信文档。
> 而且这条错得很隐蔽——它不影响任何测试，只影响下一个读这段代码的人（包括三个月后的我）。

### 15.5 ★ 数据本身的 bug：品牌和店铺名互相矛盾

上面四条都是代码。这一条是**喂给模型的输入数据**。

阶段 3 才暴露出来，原因很直接：阶段 1、2 里这些数据只是用来画图的，
"绿联的磁吸指环扣在声阔天猫旗舰店销售"画在图上看不出来；
**而阶段 3 要把这批数据整份发给模型去写分析报告**——
模型会读到每一行的店铺名，然后它可能写出"**绿联在声阔旗舰店表现突出**"这种一眼假的句子。

根因：`seed.py` 生成商品时，店铺是**从店铺模板里独立随机抽的**，
和品牌之间没有任何约束：

```python
"_shop_index": int(rng.integers(0, len(SHOP_TEMPLATES))),   # 旧：17 个模板里均匀抽，与品牌无关
```

修复前究竟有多严重，是**把 3df13cc 里的旧 `seed.py` 取出来、指向一个临时库重跑一遍**量出来的
（旧 seeder 的随机种子是固定的，所以能逐字复现修复前的数据）：

| | 品牌-店铺组合 | 其中矛盾 | 涉及商品 |
|---|---|---|---|
| **修复前** | 120 | **99** | **789 / 1000 件（78.9%）** |
| 修复后 | 20 | **0** | 0 |

也就是说，**接近八成的商品挂在一个不属于自己品牌的店铺下**。
修法是加一张显式的品牌→店铺映射，把"店铺名"从随机字段变成**派生字段**：

```python
brand_shops = {"绿联": {"京东": "绿联京东自营旗舰店", "天猫": "绿联天猫旗舰店"}, ...}
GENERIC_SHOPS = {"京东": "京东自营", "天猫": "天猫超市"}

def resolve_shop(brand_cn, platform_pick):
    shops = brand_shops.get(brand_cn, {})
    name = shops.get(platform) or GENERIC_SHOPS[platform]   # 品牌没有自家旗舰店 → 落到平台自营
    return platform, name
```

★ 一个必须守住的约束：**平台仍然在随机数流的同一个位置、用同一个 `rng.integers(0, 2)` 抽取**。
否则整个 Mock 数据集（价格、销量、价格序列）都会跟着位移一遍，
而 `test_seed.py` 里那四张标定表全部作废——**修一个显示问题，代价是推翻整个阶段 1 的实测标定**。

这条约束不能靠"我觉得我写对了"来保证，所以修完之后**拿新旧两份数据逐字段对了一遍**：
旧数据 = 3df13cc 的 `seed.py` 跑进临时库，新数据 = 当前开发库。

```
商品 1000 条，source_id 集合相同: True
逐字段差异条数：title ★相同  price ★相同  price_max ★相同  sales ★相同
                brand ★相同  platform ★相同  category ★相同
价格点 90000 条，(商品, 日期) 键集合完全相同: True
★ 同键但价格不同的点：0
```

**唯一不同的一项是价格点里的"几点几分"**（`11:33:15` vs `11:05:22`）——
那是 seeder 运行时刻的 `utcnow()`，不是随机数；序列本身是"以运行时刻为锚点往前 90 天"，
所以日期部分逐点相同、相对间距也相同。**结论：这次修复只改了店铺归属，阶段 1 的四张标定表全部有效。**

修复后的品牌-店铺自洽性：

```
品牌-店铺组合数：20      通用店铺（品牌无自家旗舰店）：160 条
★ 品牌与店铺名矛盾的组合：0
```

> **面试可讲**：这条的教训不是"生成数据要小心"，
> 而是**"这个数据到底给谁看"决定了什么算 bug**。
> 同一批数据在阶段 1、2 是完全正确的（画图不需要品牌和店铺自洽），
> 到阶段 3 才变成错的——因为**读者从"看图的人"换成了"读文本的模型"**。
>
> 还有一个小插曲值得一起讲，它是这一节里我自己犯的错：
> **我第一版校验脚本在修复后的数据上报的是"15 个矛盾"——而修复后的数据是 0 个。**
> 因为 `brand` 存的是 `"Anker/安克"` 这种中英双名格式，
> 我的脚本拿整串去比 `"Anker/安克" not in "安克京东自营旗舰店"` ——恒为真。
>
> 这个错误的方向很值得记：**它只报假阳性，不报假阴性。**
> 两种写法在修复前后两批数据上的实测对比：
>
> | | 错误写法（整串比对） | 正确写法（按 `/` 拆开） |
> |---|---|---|
> | 修复前 | 110 个矛盾 / 909 件 | **99 个矛盾 / 789 件** |
> | 修复后 | **15 个矛盾 / 840 件** ← 全是假的 | 0 个矛盾 / 0 件 |
>
> 也就是说：在**坏数据**上它虚报了 11 个（而 99 这个真实数字大得刺眼，
> 人很容易不去细究那 110 里有多少是假的）；在**好数据**上它凭空造出 15 个问题。
> **如果我当时就此去"修"，就会把一份正确的数据改坏**——
> 而修完之后错误写法依然会报错，于是我会继续修，一直到把数据改成它满意为止。
>
> 这和 §14.4 是同一类错误：**校验脚本把"什么算矛盾"重新描述了一遍，
> 而不是引用真正的定义**。区别是 §14.4 那次报的是假红（测试失败，会被追），
> 这次报的是**假阳性**（"数据有问题"，看起来像个发现）。

### 15.6 六个发现的方法论

| 发现 | 抓它的手段 | 根因 | 性质 |
|---|---|---|---|
| key 规则两处实现分叉 | 并排跑两套实现 | 同一规则写了两遍 | 代码缺陷 |
| `CreatedAt` 穿过黑名单 | 单测（问"兜底真兜住了吗"） | 只规范了大小写、漏了分隔符 | 代码缺陷 |
| `force=1` 测试假绿 | **主动怀疑已通过的断言** | ORM 身份映射 + Core 语句绕过 | 测试缺陷 |
| `tokens_used` 文档说反话 | 实测输出与文档对照 | 文档没跟着代码改 | 文档缺陷 |
| 品牌与店铺矛盾 | **换读者视角**（喂给模型前重新看一遍数据） | 字段独立随机、缺少约束 | 数据缺陷 |
| 校验脚本报假阳性（15 个） | 拿"修复后的正确数据"回头验脚本 | 校验重新描述了一遍判定规则 | 校验缺陷 |

六条里**只有两条是"代码写错了"**。另外四条分别是测试、文档、数据、**以及校验本身**的问题——
而它们在 CI 上全都是绿的，前五条全都发生在"代码已经写完、测试已经通过"之后。

第 2、5、6 三条的共性尤其值得记：**它们都不是"代码和需求不符"，
而是"我以为的保证"和"实际成立的保证"之间的差**。
`lower()` 看起来保证了同形匹配，随机店铺名看起来只是个展示细节，
`brand in shop` 看起来就是个朴素的包含判断——
三处都有一句注释（或一个直觉）在向读者保证它是周全的，而它不周全。

第 6 条还多一层：**它是"用来发现问题的那把尺子"本身有问题**。
前五条是"东西坏了，尺子量出来了"，这一条是"东西是好的，尺子说它坏了"。
后者更危险的方向是相反的：**一把只会虚报的尺子，会让人去修本来正确的东西。**

### 15.7 一条没能验证的验证点（如实记录）

阶段 3 计划里的验证点是四条：

> ① 调一次出报告；② **二次调用命中缓存**（mock client 断言 GLM 调用次数为 0）；
> ③ 打乱商品顺序指纹不变；④ 改 `PROMPT_VERSION` 指纹必变

**②③④ 已实测为绿，① 没能验证。** 原因很直接：

```
$ ls .env
ls: cannot access '.env': No such file or directory

$ curl http://localhost:8001/api/health
{"status": "ok", "app_port": 8001, "database": "sqlite", "llm_configured": false}
```

本项目没有 `.env`，也就没有 GLM API key，**因此阶段 3 的核心验收点"真的调一次模型出一份报告"
在本机无法执行**。这不是疏漏，是这类项目的固有约束：key 属于个人凭据，不该进仓库。

**替代覆盖**：`tests/test_glm_client.py` 用 `SimpleNamespace` 伪造 SDK，
并通过 `client._client = sdk` 注入（绕过 `_get_client()` 的 key 检查，结果与机器无关），
28 个测试覆盖了：三级 JSON 提取（直接解析 / 剥 markdown 代码块 / 截取首尾花括号）、
schema 校验（`{}`、缺 `headline`、`sections` 为空都要抛）、
**错误响应重试恰好一次且两次都错时在第 2 次停止**、
SDK 异常被翻译成 `AnalysisError` 且**不重试**、`response_format={"type":"json_object"}` 真的传下去了。

**但以下这些仍然未经证实**，不能因为解析层的测试全绿就说"分析功能已验证"：

1. 真实 GLM 的输出长什么样（解析层的测试只能证明"我能处理各种畸形输入"，不能证明"模型给的是这个形状"）
2. **prompt 是否真能稳定拿到 3~5 个 `sections`** ——这条只有真调一次才知道
3. 模型会不会编造数字（prompt 里要求"只引用给定数据"，但这是个**要求**不是**保证**）
4. 真实 token 消耗的量级（计划里估的是 2500~4000）

我考虑过手工塞一份假报告进 `analysis_reports` 让演示好看，**没有做**，
理由和 §14.6 完全相同：这个项目里"这些数据是真的还是造出来的"恰恰是会被问到的第一个问题，
为了演示效果造一份模型报告，等于在项目最该诚实的地方作假。

**补上这条验证的方法**（在配好 key 的机器上）：

```bash
echo "GLM_API_KEY=你的key" >> .env
uvicorn app.main:app --port 8001          # 重启
curl -X POST http://localhost:8001/api/analysis/run
curl -X POST http://localhost:8001/api/analysis/run     # 第二次应 from_cache: true
```

顺便**把第二次的 `from_cache` 和日志里"没有调用模型"一起看**——
那才是计划里 ② 真正想验的东西。**在那之前，它是一处已知缺口，不是已完成项。**

## 十六、真实采集与采集调度的实测发现（阶段 4）

阶段 4 写完了 `scraper/sources/{smzdm,mock}.py`、`scraper/worker.py`、`app/api/tasks.py`
和 `tests/test_tasks.py`（37 条），并把 `base.py` 的降级链、`dedup.py` 的品牌处理、
`seed.py` 的标题生成都改了一轮。全库测试 **399 → 500 全绿**。

这一节记十三件事，它们的共同形状和上一节一样：**没有一件是"功能没写出来"**。
真正的情况是——阶段 4 是全项目第一次把两条此前各跑各的线接起来：

```
        （阶段 1~3）seed 直写 ──▶ 数据库 ──▶ API ──▶ 图表
                          ╲
                           ╳   ← 这两条线在阶段 4 之前【从没在同一个进程里出现过】
                          ╱
   （阶段 4）真实页面 ──▶ 采集管道 ──▶ 归并 ──▶ 数据库
```

接起来之后暴露的问题，绝大多数不是"某一侧写错了"，而是**两侧各自都正确、
但它们之间的某个假设从没被写下来过**。§16.7 和 §16.8 是这一类的两个标本。

| 在哪一节 | 藏在哪里 | 一句话 |
|---|---|---|
| 16.1 | 计划 | 写在降级链里的第一层，从头到尾没被证实存在过 |
| 16.2 | 页面事实 | 计划里的第二个源不是好价页，是 UGC 晒物，还带用户昵称 |
| 16.3 | **注释** | "带 probe 就是被拦"——而正常页面也带它 |
| 16.4 | 真实数据 | 归并逻辑第一次考试：0 次误合并，但也 0 次合并 |
| 16.5 | **验收点** | 「多点价格序列」在真实数据上一条也拿不出来 |
| 16.6 | 算法 | 无空格中文标题上，相似度退化成了"有没有共用品牌词" |
| 16.7 | **两个模块之间** | seed 的标题有 42% 重名，藏了三个阶段 |
| 16.8 | **两种表示之间** | 品牌有两种形态，导致硬门槛静默失效 |

### 16.1 ★ 降级链里的第一层，从头到尾没被证实存在过

计划里（本文档第二节、第十节）写的是三层降级，而且给了它一个很漂亮的叙述：

```
尝试解析 JSON 接口  ──失败──▶  尝试解析 HTML  ──失败──▶  Playwright 渲染
     (最快)                        (中等)                  (最慢，最后手段)
```

真去看页面才发现：`/jingxuan/` 的数据**就在服务端渲染的 HTML 里**
（`<ul id="feed-main-list">` 下的 `<li class="J_feed_za feed-row-wide">`）。
没有任何 XHR 接口在给它供数——**"JSON 层"是一个我在计划阶段想当然写下的东西，
从来没有被验明正身。**（当时让我以为它存在的那个信号，是 §16.3。）

处理方式是把它删掉，而不是"留着反正也不占地方"。理由：

- 一个从未被跑通过的层，**只会让代码看起来比它的实际能力更强**。
  面试官问一句"JSON 接口的响应长什么样、你怎么发现它的"就露馅了。
- 更要紧的是它会**改变别的代码的形状**：`SmzdmSource.fetch()` 里要留
  一个"先试 JSON"的分支，`Layer` 元组里要多一项，测试要覆盖它——
  于是你会为一条不存在的路径付出真实的维护成本。
- 最终落地的两层是：

```
  第 1 层  html      httpx 拿页面 + 正则解析          ← 唯一被真实数据验证过的
  第 2 层  browser   Playwright 渲染后再交给第 1 层   ← 结构就位，默认关闭
```

**第 2 层保留但默认关闭**，也是有理由的：唯一的作用是"万一哪天改成前端渲染了"，
而代价是 `playwright install chromium` 要下 150MB 二进制。
为一个用不上的降级层让每个 clone 项目的人都下 150MB，不划算。

> **教训**：降级链的层数不是设计自由度，是**实测结果**。
> 写进降级链的每一层，都应该能指出一次它真实解析成功的记录；
> 指不出来的那一层，写进文档就是虚报能力。

### 16.2 ★ 计划里的第二个源不是好价页，是 UGC 晒物

计划原文是「`/jingxuan/` + 分类好价页」双源。真去看了 `fenlei/shujuxian`、
`fenlei/shumapeijian` 这些页面之后发现，它们**不是好价页**：

| 检查项 | 精选页 `/jingxuan/` | 分类页 `fenlei/*` |
|---|---|---|
| 卡片结构 | `<li class="J_feed_za feed-row-wide">` | `shaiwu-card-container`（**晒物**） |
| 链接指向 | `www.smzdm.com/p/182950953/` | `post.smzdm.com/talk/` |
| `articleid` | 有 | **没有** |
| `timesort` | 有 | **没有** |
| 价格 | `z-highlight` 里有 | **没有** |
| 正文 | 商品标题 | 用户写的使用感受（"做工质感：尼龙绳做工，相比原装线的橡胶材质…"） |
| 额外字段 | —— | **`nickname`（用户昵称）** |

两个**各自独立成立**的排除理由：

1. **数据模型对不上**：没有 `timesort` 就没有价格时间点，没有价格就没法算
   `price_history`。抓回来只能存成一条"帖子"，而本项目没有这个实体——
   要为它建一张表、配一套接口和一个页面，只为了一半的字段。
2. **★ 合规红线**：晒物卡片里带用户昵称，属于个人信息。
   项目从一开始就定了"只取商品公开字段、不收集个人信息"，
   所以这里不是"顺便也能抓"，是**明确不抓**。

第 2 条单独就够了——**即使分类页的数据模型完美匹配，也不该抓它**，
因为代价是项目最开头那句合规承诺("不收集个人信息")变成一句空话。

代价是品类覆盖变窄（只剩 `/jingxuan/` 的全站好价，没有"数码配件"这种定向类目），
这个取舍如实记在这里。

> 实现上，这条没写成文档备注，而是写成了一条**可执行的判据**：
> `RE_UGC_MARKER = re.compile(r"shaiwu-card-container|post\.smzdm\.com/talk/")`，
> 认出来就拒绝。理由很实在——**文档拦不住"我改天把 URL 换成分类页试试"**，
> 而代码拦得住，并且会把它单独计成 `pages_ugc` 而不是 `pages_unparsed`。

### 16.3 ★ `probev3.js` 是假信号：正常页面也带它

spike 阶段的注释里写着：「带 `probe.js` 就是被 WAF 拦了」。

**这句话是错的。** 拿真实页面 fixture 一比就露馅：

| fixture | 体积 | 含 `probev3.js`？ | 含 `feed-main-list`？ | 跳 `/404`？ |
|---|---|---|---|---|
| `smzdm_jingxuan_page1.html` | 346003 | **有** | 有 | 否 |
| `smzdm_jingxuan_page2~5.html` | 310K~321K | **有** | 有 | 否 |
| `smzdm_waf_block.html` | **185** | **有** | 没有 | **是** |

`probev3.js` 是**注入到每一个响应里的 WAF 信标**，正常页面同样带着它
（6 个 fixture 里 6 个都有）。拿它当"被拦截"的判据，会把所有正常页面判成拦截，
表现为**全站抓取直接失效**——而且症状是"一页都没抓到"，
看起来像"今天站点挂了"或者"URL 全填错了"。

它当时之所以没造成误判，纯属侥幸：代码里真正起作用的是**另一条判据**
（响应体小于 5000 字节）。**一条错的判据和一条对的判据并排待着，
看上去就是两条判据都对。** 这和 §15.2 是同一个形状：
`lower()` 看起来保证了同形匹配、这句注释看起来保证了拦截能被识别——
两处都有一句话在向读者保证它是周全的，而它不周全。

真正区分两者的判据（现在是 `looks_blocked()`）：

```
正常页  300KB+，有 <ul id="feed-main-list">
拦截图  185B，  <meta http-equiv="refresh" ... url=https://www.smzdm.com/404>
```

> ★ 这条能成立，靠的是 `tests/fixtures/` 里**存了那两个真实文件**。
> 如果没有把真实页面留档，这个 bug 只会在**下一次真联网抓取**时才暴露——
> 而那时候 SMZDM 的 WAF 已经封过一轮了（§12.1），意味着验证成本已经付不起了。
> **把真实响应存成 fixture，价值不只是"给测试用"，更是"让这类判据可被检验"。**

这也是为什么重放语料里**故意留着那张 185 字节的拦截图**：
每次重放都会走到"有 1 页被拦截"这条路（见 16.12 的实测输出），
否则拦截检测就只有在真联网那天才会第一次运行。

### 16.4 ★ 归并逻辑在真实数据上的第一次考试

100 条真实爆料（5 个唯一页面）灌进开发库的实测结果：

```
解析 100 条，新商品 94，待核对 6，新增价格点 98
```

（这一行就是 `CrawlReport.as_message()` 的真实输出——`归并 0` 和 `刷新 0`
不会出现在里面，因为那两项为零时会被省略。）

把灰区那 6 对逐对摊开（`MERGE_THRESHOLD = 0.75`，`GREY_ZONE_THRESHOLD = 0.50`）：

| # | 候选（新） | 目标（已存在） | 包含度 | 判定 |
|---|---|---|---|---|
| 1 | 斯凯奇 5折 舒适缓震 女士跑鞋 | 斯凯奇 5折 女士轻质老爹鞋 | 0.667 | 真阴性 ✅ |
| 2 | 斯凯奇 5折 男鞋秋季休闲皮鞋 | 同上 | 0.667 | 真阴性 ✅ |
| 3 | 斯凯奇 5折 女鞋摩卡熊 复古老爹鞋 | 同上 | 0.667 | 真阴性 ✅ |
| 4 | 斯凯奇 5折 男厚底增高缓震老爹鞋 | 同上 | 0.667 | 真阴性 ✅ |
| 5 | 斯凯奇 5折 Slip-ins闪穿 男士健步鞋 | 同上 | 0.667 | 真阴性 ✅ |
| 6 | 米良品 创意电动发光自吸掏耳神器 | 米良品 家用便携可折叠购物车 | 0.500 | **灰区假阳性** ⚠️ |

**这场考试真正要看的不是"合并成功了几对"，而是"有没有误合并"。**
误合并是不可逆的：两条不同商品的爆料被挂到同一个 `product_id` 之下，
两条真实的价格就进了同一条时间序列，从此那条序列上的每一次涨跌都是假的——
而且它长得跟真的一样。所以自动合并线（0.75）和真实数据里最高的一对（0.667）
之间那段余量，是这一节最值钱的一个数字。

5 对斯凯奇是**真阴性**：同品牌、同品类、同折扣、不同款式。
token 高度重叠但确实是不同商品，**归并逻辑正确地拒绝了合并**。
第 6 对是灰区的一次假阳性，代价是"多让人看一眼"，
原因是可解释的，见 §16.6。

**没有为这一对去调阈值**，理由在 §16.6 末尾——简单说：
**拿单个数据点去凑参数，就是在给数据拟合噪声。**

### 16.5 ★ 一条无法在真实数据上演示的验收点（如实记录）

阶段 4 计划里的第三条验收点是：

> 若同一商品被多次爆料，其价格历史出现多个点

**实测结果是：一条也拿不出来。** 开发库里现在的真实数据是：

| 指标 | 实测 |
|---|---|
| `source='smzdm'` 的商品 | 100 |
| 价格点 | 98 |
| **有 ≥2 个价格点的商品** | **0** |
| 有 0 个价格点的商品 | 2（卡片上没写价格，见 `RawDeal.price_raw` 允许 None 的设计） |
| 归并发生的次数 | **0** |

原因不复杂：**归并的用武之地是"同一商品跨天重复爆料"，
而我只抓了一次快照。** 100 条爆料是同一时刻的 100 个不同商品。

> ★ 必须说清楚的一件事：**"那我多抓几页不就行了"不能解决它。**
> 同一时刻抓 10 页只会得到 200 个**不同**商品，不会凭空产生第二个价格点。
> 要演示这条验收点，需要的是**真实的时间流逝**——隔几天再抓一次同样的页面，
> 看那一天新出现的爆料里有没有和已有商品撞上的。
> 而那是要花掉 WAF 请求额度的（§12.1），额度已经用掉一轮了。

**替代覆盖**：这条路径在测试里是覆盖了的——
构造的爆料序列走完"归并 → 挂到同一 `product_id` → 第二个价格点"全程，
`test_price_history.py` 里另有 `ON CONFLICT DO NOTHING` 的回归测试
（同一 `(product_id, source_ref)` 重复写入既不抛异常也不产生第二行）。

**但测试覆盖不等于真实验证。** 测试证明的是"这条路能走通"，
它证明不了"真实爆料里真的会出现同一商品的第二次爆料"——
而这恰恰是这条验收点想问的问题。

> 这和 §15.7 是同一类记录：**一处已知缺口，不是已完成项。**
> 补上它的方法就写在 §16.12 的表里，而不是含糊过去。

### 16.6 ★ 无空格中文标题上，相似度退化成了"有没有共用品牌词"

§16.4 第 6 对假阳性的根因，值得单独记——因为它是一个**真实的方法论局限**，
不是一处可以顺手修掉的疏漏。

`dedup.tokenize()` 只按空格切（有意为之，见 `dedup.py`：
不引 jieba 是为了**结果可复现**）。后果是中文标题里**没有空格的时候，
整个句子变成一个 token**：

```
"米良品 创意电动发光自吸掏耳神器"  →  {米良品, 创意电动发光自吸掏耳神器}    2 个 token
"米良品 家用便携可折叠购物车"      →  {米良品, 家用便携可折叠购物车}        2 个 token
                                      交集 = {米良品} → 包含度 = 1/2 = 0.500
```

0.500 正好等于灰区下界，于是这一对被标记成"疑似重复"。

**也就是说：在这类无空格中文标题上，这个分数退化成了
"两个标题有没有共用品牌词"**，而不是真正的语义重叠度。

顺着这条看，斯凯奇那 5 对拿到 0.667 而不是更高，也有一半是运气——
它们的标题里**恰好**有空格，所以被切成了更多 token。
换句话说，**同一个算法在"有空格的中文标题"和"没空格的中文标题"上
表现出的严格程度是不一样的**，而这件事在分数上完全看不出来。

**为什么不把阈值调到 0.51 排掉这一对：**

- 自动合并线在 0.75，真实数据里最高的对是 0.667，**安全余量真实存在**；
- 灰区假阳性的代价是"多让人看一眼"——而调阈值去排掉它，
  会让**下一个**落在 0.49x 的真阳性被漏掉，那个代价是污染价格序列；
- 用单个数据点定阈值，正是 `dedup.py` 开头批评的那种拍脑袋做法。

**真正该修的是分词**（用 jieba 或加一层中文短语切分），
但那会把"结果可复现"这条性质换掉——jieba 的切分随词典版本变化，
同一个商品在不同时间可能给出不同的归并结论。**这是个明确的取舍，不是疏忽**，
所以记在这里，而不是偷偷绕过去。

### 16.7 ★★ seed 的标题有 42% 重名，藏了三个阶段

这一条是全节最值得讲的，因为它的**症状和原因隔了三个阶段**。

**症状**：Mock 源采了 100 条爆料，结果只建出 **64 个商品**。
报告写着"新商品 64"，而库里的 Mock 商品本来是 100 个。

**原因**：`seed.build_products()` 抽模板、抽片段、抽颜色时是**各自独立**抽的
（有放回），于是大量商品拿到了重复标题。实测：

| 商品数 | 不同标题数 | 重复率 | 最多重复几次 |
|---|---|---|---|
| 100 | 87 | **13%** | —— |
| 1000 | **583** | **42%** | 19 次 |

**为什么三个阶段都没发现**——这句是重点：
**从来没有任何东西拿归并逻辑跑过 Mock 数据。**

- `seed.py` 直写只关心 `(source, source_id)` 唯一约束，标题重不重复无所谓；
- 前端图表也不在乎（同样的标题在表里显示两行，看不出来）；
- §13 那一节的 self-check 检查的是价格分布、销量梯度、价格序列形态，**没有一条看标题**。

直到阶段 4 把采集管道接上 mock 源，归并逻辑**第一次**看见这批数据：
它看到一个 `source_id` 已有主、但标题和**别的**商品一模一样，
于是判定"这是重复爆料"，**静默地少建了 36 个商品**。

> ★ 归并**少建商品**不报错——这正是它藏了这么久的原因。
> 如果它抛一个异常，这个问题在阶段 4 的第一分钟就会被发现。

**修法**：`_pick_title()` 维护一个 `seen_titles` 集合，重抽直到标题唯一；
抽不出来（池子真的用尽）就抛带池子大小的 `RuntimeError`，
而不是悄悄返回一个重复的。实测标题池约 **4039** 个，撑 1000 个有余量。

**回归测试取 1000 而不是 100**：100 那次只重了 13%，1000 那次重了 42%，
**取满量程才能守住真实场景**。断言里还多一条：`title_norm` 也必须唯一——
归并比对看的是归一化后的形式，两个原始标题逐字不同但归一化后相同
（比如只差一个被当噪声词去掉的"包邮"）照样会被判定成重复。

> **教训**：seed 不要求标题唯一，归并也没写错。
> 问题在两者之间的**隐式假设**——"标题是天然不同的"——
> 而这个假设**没有写在任何地方**，所以既没有测试守着它，
> 也没有人在 review 时想到它。这类假设只能在两个模块第一次接起来时暴露。

### 16.8 ★★ 品牌有两种形态，导致硬门槛静默失效

`products.brand` 这一列曾经有两种格式，**取决于数据从哪个入口进来**：

```
seed.py 直写   →  "Soundcore/声阔"     （双语、保留大小写，给人看的）
采集管道写入   →  "soundcore|声阔"     （小写、已排序、给机器比的）
```

后果不只是"显示不一样"。`brands_compatible()`（硬门槛第 1 条）
靠 `"|"` 拆分品牌的两段，而 `"Soundcore/声阔"` 里**没有 `"|"`**，
会被当成**一个整体**去比——

> 于是**同一品牌的 Mock 商品和真实商品，在硬门槛上永远匹配不上**。
> 而这种失败是**静默的**：归并只是"没合并"，不报错。
> 更糟的是，它跟 §16.4 那条"0 归并"的现象长得一模一样，
> 会让人以为"真实数据里本来就没有可归并的对"。

**修法**是把两件事彻底分开——**和 token 的处理方式完全一样**：

```
库里存什么   →  显示形态（display_brand），给人看、给界面用，从不参与比对
比对时用什么 →  规范形态（extract_brand），现算，从不落库
```

两条性质都成立：

- `display_brand` 只压空白：**不小写、不换分隔符、中间空白不动**；
- `extract_brand` 是**幂等**的——喂规范形态进去返回它自己：
  `"Soundcore/声阔"` → `"soundcore|声阔"`；`"soundcore|声阔"` → `"soundcore|声阔"`。
  幂等很重要，因为它让调用方**不必知道手上的字符串是哪种形态**：
  采集管道拿的是源站原文，`load_existing` 拿的是库里的显示形态，
  两边都直接喂进去就对。少一个"这个字段现在是什么格式"的隐式约定，
  就少一整类只在某个入口才出现的 bug。

**实测**：真实数据里 100 个 smzdm 商品有 **61 个** brand 带 `"/"`
（`RIMEI/金达日美`、`whisper/护舒宝`、`LUZHOULAOJIA/泸州老窖`…），
另外 39 个是单段（`友谊`、`希尔顿`、`京东鲜花`）；Mock 侧同样是显示形态
（`ROMOSS/罗马仕`、`Anker/安克`）。两种形态现在**写进库的是同一回事**。

> 这条和 §15.1（同一套 key 规则写了三遍、两份已经分叉）是同一个形状：
> **同一件事有两种表示，而它们之间的转换没有被写下来。**
> 区别是 15.1 那次是意外分叉，这次是设计出来的——
> 但"库里存什么"和"比对用什么"这两个问题分不清，照样出事。

### 16.9 ★ 把"没允许联网"说成了"被拦截"

这是被一次**真实的输出**逼出来的：

```
队列里有一个 source=smzdm 的任务，用【默认参数】跑 worker
  → 任务失败。失败信息（crawl_tasks.message，前端直接显示的那一行）写着：

        被拦截，已按约定停止（不重试）
```

**而当时一个网络请求都没发出去。**

错的不是程序——它确实停下来了，也确实没有联网，行为完全正确。
错的是**这句话把"不允许"说成了"被拒绝"**。
照着那句话去查，方向是 WAF 封禁、User-Agent、请求频率；
真相是命令行**少了一个 `--allow-network`**。

两者该触发的动作是**截然相反**的：

| | 含义 | 该怎么办 |
|---|---|---|
| `FetchBlocked` | 对方在挡我们 | 别重试、别加频率、**今天别采了** |
| `NetworkDisabled` | 我们自己关着开关 | 加 `--allow-network` 就行 |

用一个类型表示两件事，失败信息就只能是笼统的"采集停止"——
而那句笼统的话会**把人带去研究 WAF**。所以拆成两个异常类型，
`fail_task()` 里两条分支给出完全不同的 message，`NetworkDisabled` 那条
连修法都直接写出来：

```
未联网（不是被拦截）：…
★ 修法：加 --allow-network 走真网络，或加 --replay 走离线重放。
```

**顺带修掉的第二个问题（同一类）**：`fail_task()` 一开始对**所有**失败
打 `logger.exception`。跑一次 `worker --once`（没联网），日志里出现
**20 行 Python 堆栈**，看起来像程序崩了——而它其实规规矩矩地把任务标成失败、
写好了修法。**把正常行为显示成崩溃，会让人去修一个不存在的问题。**
改成"预期内失败走 `logger.warning`，其余走 `logger.exception`"，
实测日志从 20+ 行降到 **4 行**。

> **一个测试写法上的反例（我自己踩的）**：最初的断言写成
> `assert "拦截" not in task.message`，结果**失败**了——
> 因为我自己写的那句用来预先打消错误诊断的话里，
> "未联网（**不是被拦截**）"恰好含"拦截"两个字。
> 改用 `FetchBlocked` 分支的独有措辞作判据（`"已按约定停止" not in`、
> `"不重试" not in`）。
> **断言比它要守的规则更严，就会惩罚正确的实现。**

### 16.10 ★ SQLAlchemy 批量 UPDATE 之后：库里是对的，读的人看到旧的

**症状**：测试里读出来的 `task.message` 是 `None`，而用 SQL 直接查库，那一列有值。

**根因**：`recover_stale_tasks()` 和 `claim_next_task()` 都用"带条件的批量 UPDATE"，
而 **SQLAlchemy 2.0.54 的 `session.execute(update(...))` 不会把新值
同步到已经在会话里的对象上**。实测三种 `synchronize_session` 策略：

| 策略 | `status` 同步？ | `message` 同步？ |
|---|---|---|
| `auto`（默认） | 不可靠 | 不可靠 |
| `evaluate` | ✅ | **❌** |
| `fetch` | **❌** | **❌** |

**而数据库里的行是对的**——所以这是一个纯粹的"读的人拿到旧值"问题，
和本项目反复踩到的"价格静默变旧"是同一类。

**修法**：在 `db.commit()` 之后显式 `db.expire_all()`，并把实测结果写成注释。
代价是这次会话里的对象全部过期、随后的访问各多一次 SELECT——
这两个函数一轮启动只跑一次，这点开销可以忽略；**而"读到旧值"不可接受**。

> ★ 这个坑在**认领任务**这条路径上尤其危险：
> 认领会把 `progress` 清零、`total` 置空。如果会话里那个对象还带着
> **上一次运行**的 `progress=100`，那么紧接着写进度时就会从 100 开始，
> 于是前端看到**一个一开始就满的进度条**——而它看起来像"任务瞬间跑完了"。

## 十七、告警链路的实测发现（阶段 5）

阶段 5 做的是"采集 → 告警"这条闭环的后半段。落地的文件：

| 文件 | 是什么 |
|---|---|
| `scraper/check_alerts.py` | 三态状态机（armed / fired）+ 两种规则判定 |
| `tests/test_alerts.py` | 41 条，守状态机与纯函数边界 |
| `app/api/alerts.py` | 规则 CRUD + 触发记录 + 手动查一轮 |
| `tests/test_api_alerts.py` | 61 条，守接口的"放进来什么、说出去什么" |
| `scraper/worker.py` | 每 300 秒叫一次检查器；`--once` 也查一轮 |

全库测试 **602 passed**。

### 17.1 为什么必须有状态：一个可算出来的数字

最直觉的写法是"价格 < 阈值 → 写一条 alerts"。它在价格**持续**低于阈值
期间，每查一次就写一条：

```
5 分钟查一轮 → 一天 288 轮 → 288 条记录、288 条通知
```

而"这个商品跌破 200 元"这件事**只发生了一次**。没有状态的告警把
**一个状态**当成了 **288 个事件**。用户收到的通知会从"值得看一眼"
变成"垃圾"，于是没人再看——这就是"告警疲劳"的成因，
而它在这里是可以被算出来的，不需要等用户投诉。

状态机四条规则：

```
armed + 条件成立   → 触发：写 alerts、state ← fired
fired + 条件成立   → 跳过（同一个事件，不重复记录）
fired + 条件不成立 → 重新武装：state ← armed（★ 不发通知）
armed + 条件不成立 → 什么也不做
```

**"重新武装"必须存在**，否则：

```
跌到 199 → 触发 → 涨回 250 → 又跌到 180
```

第二次跌破是一个**新的**价格事件，永久熄火的话它会被漏掉，
而且漏得悄无声息——用户以为"规则还在看着"。

**"重新武装不发通知"**：一次价格波动会产生两条通知（跌破一条、涨回一条），
而涨回那一条对用户没有任何可执行的信息——他既不需要买，也不需要卖。
代价是"已经重新武装"只能从 `state` 字段看出来，**所以界面必须显示它**。

### 17.2 ★ 真实数据上的跌幅规则：98% 的商品让它永远静默

这一条是本阶段最重要的实测发现，而且它是 §16.5 的**告警版本**。

对 `data/ecom.db` 里的价格点做了一次只读统计：

| 数据源 | 商品数 | 有价格历史点 | 单商品最多点数 |
|---|---|---|---|
| mock | 1000 | 1000 | 90 |
| **smzdm** | **100** | **98** | **1** |

真实数据的点数分布：

```
0 个点：  2 个商品
1 个点： 98 个商品
2 个点及以上：0 个商品
```

这意味着，给任何一个真实商品配"跌幅 ≥ 20% 就提醒我"：

- **1 个价格点的 98 个商品**：跌幅的基准 = 那唯一的价 = 当前价 →
  **跌幅恒为 0，永远不触发**；
- **0 个点的 2 个商品**：算不出基准 → 每轮记一条"判不了"。

★ 关键在于**第一种**：它不报错、不算"判不了"、状态机一切正常、
界面上安安静静——它和"规则在正常工作，只是价格还没到"**完全无法区分**。

§16.5 记的是"多点价格序列画不出来"（图表是空的，**看得见**）；
这一条记的是"跌幅规则永远不触发"（**看不见**）。
同一个根因，第二种表现形式更危险：空图会有人问，静默的规则不会。

### 17.3 由 17.2 推出的接口行为：警告，而不是拒绝

既然 98% 的真实商品都是这个状态，接口就不能假装没这回事。
但**不能拒绝**这种规则——它不是错的，只是**还没到时候**：
商品被再次爆料时会多出第二个价格点，那时这条规则立刻就有意义。
拦下来等于禁止用户提前配好。

所以照建，但把话说在前面。实测的响应原文（真实商品 1100，
它只有 1 个价格点，`source_ref=183087216`）：

```
规则 #2 state=armed
warning: 这个商品目前只有 1 个价格点，跌幅的基准就是当前价，所以跌幅恒为 0
        ——这条规则【在它出现第二个价格点之前不会触发】。
        ★ 第二个点要靠这个商品被再次爆料（见 docs/可行性评估.md 16.5）。
```

三条设计细节：

1. **提示放在后端响应里，不放在前端**：前端要算它就得自己查一遍
   `price_history`，那是第二份实现；而且 curl 的人、将来别的客户端看不到。
2. **警告 ≠ 拒绝**：规则照样建出来了，`total = 1`；
   拦下来是错的，因为它将来会有用。
3. **有 2 个点时不能提示**：这条反证是必要的——
   少了它，一个"跌幅规则一律提示"的实现也能让前两条测试变绿，
   而那样的提醒很快会变成谁都不看的噪音。
   `test_drop_pct_with_two_points_does_not_warn` 守着这条。

### 17.4 改规则 = 重新武装（一个静默空洞的推理）

这一条不来自实测，来自把状态机的边界推到底。少了它会出现：

```
规则"低于 100 提醒我" → 跌到 99 → 触发，state=fired
→ 用户觉得阈值太低，改成"低于 200 提醒我"
→ 当前价 99 < 200，条件成立，但 state 还是 fired → 跳过
→ 用户以为改完就会响，实际它永远不会响（除非价格先涨回 200 以上）
```

所以改阈值 / 改规则类型 / 改启用状态，一律回到 `armed`。
**代价是改完可能立刻收到一次通知**（因为条件当下就成立）——
这是对的：用户刚刚亲手要求了"这个条件下提醒我"。

配套的一条同样重要：**空 PATCH 不能重置状态**（"保存了一下但什么都没改，
于是重新武装了"是个很难查的怪事）。实现上就是那个 `if changed:` 分支。

### 17.5 接口层的另外三个决定

| 决定 | 不这么做会怎样 |
|---|---|
| `rule_type` 的合法值**只取** `check_alerts.RULE_TYPES`，不在接口层另写一份 Enum | 加了新规则类型时改了元组忘了枚举 → 接口把**合法**的类型挡在门外。★ 代价是 OpenAPI 上它是个自由文本框而不是下拉框——选了"正确"而不是"文档好看" |
| 重复规则在**建成和改成两处**用同一个函数挡 | 只挡建成的话，把 A 的阈值改成和 B 一样就绕过去了，一个价格事件写两条 alerts。★ 这不是"两处实现不一致"，是**一处有一处没有** |
| 删规则时**显式**删掉它的 alerts，不用 `ON DELETE CASCADE` | 本项目没有迁移工具，`create_all` 不改已有的表——模型上加 `ondelete="CASCADE"` 只对**新建的库**生效，于是同一份代码在两台机器上行为不同 |

### 17.6 变异测试：三处设计各被哪条测试咬住

改完实现之后，把三处关键设计各自**弄坏一次**，看测试是否变红：

| 变异 | 变红的测试 |
|---|---|
| 去掉 PATCH 里的去重 | `test_patch_cannot_create_a_duplicate` |
| `delete(Alert)` 漏掉 where | `test_delete_does_not_touch_other_rules_alerts` |
| 空 PATCH 也无条件重新武装 | `test_empty_patch_leaves_state_alone` |

**"弄坏它必须变红"才是**——这正是 §16.12 里那条"验收点兑现表"
在阶段 5 的用法。

| 常驻循环的时间节流 | `worker.main()` 里 `--once` 之外的接线（每 300 秒查一次的那段）**没有自动化测试**。测它要伪造 `time.monotonic` 和轮次，代价大于收益——但这是个已知的裸区，不是"测过了" |

## 十八、图片代理的实测发现（阶段 5 续）

### 18.1 先去看了一眼数据：图只有真实采集的才有

开工前的一轮勘察（`?source=` 分别查一遍）：

| 数据源 | 有 `image_url` 的商品 | 域名分布 |
|---|---|---|
| `mock` | **0 / 1000** | — |
| `smzdm` | **97 / 100** | **全部在 `y.zdmimg.com`**，无一例外 |

样例：`https://y.zdmimg.com/202609/16/6aaa2bbd797765259.jpg_d200.jpg`

三件由此确定的事：

1. **列表接口不用改。** `ProductListItem` 里已经有 `image_url` 和 `url` 两个字段
   （阶段 1 建表时留的），前端直接取即可。
2. **占位符是必需品，不是装饰。** Mock 视图下 100% 没有图，
   `?source=all` 的每一页也大部分没有。如果"没有图"表现为一个破图图标，
   那这一页看起来就像坏了——而它其实是正常的。
3. **白名单只需要两个域名。** 勘察结果直接决定了 `ALLOWED_IMAGE_HOSTS`
   写 `zdmimg.com` + `smzdm.com` 就够，不需要开任何口子。

> ★ 顺带一个踩到的观察：有一条 URL 的路径是 `.png` 结尾，但后缀是 `_d200.jpg`
> （`...6ab97ab04ee96864.png_d200.jpg`）。也就是说**不能从 URL 后缀推断图片类型**——
> 类型只能信响应头。这正是下面 §18.4 那条"必须检查 Content-Type"的另一个理由。

### 18.2 ★ 白名单挡的是"名字"，真正被连接的是"地址"

这是整件事里唯一一处**必须实测才能确定写法**的地方，两个探针脚本的结论：

**探针一：`ipaddress` 认不出多少种写法？**

| 主机名写法 | `socket.inet_aton` | `ipaddress.ip_address` |
|---|---|---|
| `127.0.0.1` | ✅ | ✅ |
| `2130706433`（十进制整数） | ✅ → 127.0.0.1 | **❌ 不认** |
| `0x7f000001`（十六进制） | ✅ → 127.0.0.1 | **❌ 不认** |
| `0177.0.0.1`（八进制） | ✅ → 127.0.0.1 | **❌ 不认** |
| `127.1`（少写两段） | ✅ → 127.0.0.1 | **❌ 不认** |
| `evil.com` | ❌ 抛 OSError | ❌ 抛 ValueError |
| `8.8.8.8 `（**带尾随空格**） | **✅ 成功** | ❌ |

四个变体 `ipaddress` 一个都不认，而浏览器和 `inet_aton` 都认。
**所以两道判断必须都有**——只写 `ipaddress` 的话，`http://2130706433/`
会被当成一个普通主机名，进白名单检查（不通过，403），
但那条路径上它**已经走到 DNS 解析**了。

最后一行更阴：`inet_aton("8.8.8.8 ")` 是**成功**的。
这就是"为什么要在结构化解析**之前**先扫一遍空白和控制字符"的实测依据——
不扫的话，会存在"我们判非法、某个下游判合法"的分叉，
而分叉就是绕过点（不需要两边都错，只要两边不一致）。

**探针二：`is_global` 覆盖了哪些内网形态？**

| 地址 | `is_private` | `is_global` |
|---|---|---|
| `127.0.0.1` / `10.0.0.1` / `172.16.0.1` / `192.168.1.1` | True | False |
| `169.254.169.254`（云元数据端点） | True | False |
| `100.64.0.1`（运营商级 NAT） | **False** | **False** |
| `198.18.0.1`（基准测试段） | True | False |
| `0.0.0.0` | True | False |
| `::1` / `fc00::1` / `fe80::1` | True | False |
| **`::ffff:127.0.0.1`**（IPv6 写法的回环） | True | **False** |
| `8.8.8.8` / `93.184.216.34` | False | True |

**结论：用 `is_global` 一个谓词，不用手写私有段清单。**

注意 `100.64.0.1` 那一行——它 `is_private` 是 **False**。
手写清单是"照着记忆里的私有段写一串"，而记忆里通常只有
`127./10./172.16-31./192.168.` 这四段（原始需求文档里写的正是这四段）。
漏掉 `100.64/10` 或 `198.18/15` **不会报错**，只会放行——
手写清单的失效方式是静默的，而 `is_global` 是 stdlib 里最严的那个谓词。

最后一行是"两种写法指向同一个东西"的标准案例：只查 IPv4 私有段的实现
会放 `::ffff:127.0.0.1` 过去。

### 18.3 ★ 诚实的残余风险：两次解析之间的窗口

本模块的流程是：**我们解析一次 → 检查 IP → 交给 httpx 去请求**，
而 httpx 请求时会**再解析一次**。两次解析之间有一个时间窗口，
恶意 DNS 可以在这期间把答案从"公网 IP"换成 `127.0.0.1`
（DNS rebinding / TOCTOU）。

**这个窗口没有被关掉。** 彻底关掉它需要"把连接钉死在已经校验过的那个 IP 上"
（自定义 transport 覆盖 DNS 解析，或直连 IP 再手工设 Host 头），
代价是 TLS 的 SNI 和证书校验要自己处理——对一个只放行两个图床域名的代理来说不值得。

所以四道闸门能做到的是：**把攻击面收窄到"攻击者必须同时控制一个白名单域名的 DNS"**。
这条写进了 `app/api/images.py` 的模块文档字符串，因为它属于
"面试官问一句就能问出来"的那类东西——主动说比被问出来好。

### 18.4 同源 XSS：代理的坏法和 SSRF 完全是两回事

SSRF 是"让服务器去读它不该读的"，而同源 XSS 是"让浏览器把攻击者的内容当成我们的页面"。

路径很短：代理在**同源下**返回第三方内容 → 上游返回一段 HTML →
用户点开 `/api/proxy-image?url=...` 这个链接 → 脚本在**我们的源**上执行，
能读 localStorage（里面有数据源选择）、能带着 cookie 调我们的接口。
（跨域的 `<img src>` 出不了这个事，所以说到底不是图片的问题，是代理的问题。）

三重防护，每一重都对应一个具体的绕过方式：

| 防护 | 挡的是什么 |
|---|---|
| 上游 `Content-Type` 必须是 `image/*`，否则整条失败 | 直接返回 HTML |
| **`image/svg+xml` 单独拒绝** | SVG 是合法的 `image/*`，但作为顶层文档渲染时内联 `<script>` **会执行**——所以"以 image/ 开头"这条规则单独用不够 |
| 响应带 `X-Content-Type-Options: nosniff` + CSP | 一个 content-type 写着 `image/png`、内容其实是 HTML 的响应，被直接导航打开时仍可能被渲染 |

第三条不能省：它是唯一能防住"类型说是图片、内容不是"的那一重。

### 18.5 重定向 = 白名单的旁路（一个能实测的洞）

```
http://y.zdmimg.com/x.jpg  →  302  →  http://127.0.0.1:8001/api/analysis/latest
```

第一跳**完全合法**：白名单成立、协议成立、域名不在内网。
如果实现是"检查一次 URL，然后 `follow_redirects=True` 交给 httpx"，
第二跳一次闸门都不会经过——**白名单就成了一张贴在门上的纸**。

本项目的做法：`follow_redirects=False`，自己跟，**每一跳从 `_validate` 重走一遍**，
最多 3 跳。上限定成 3 不是洁癖：这个端点写成了同步 `def`（跑在线程池里），
一个永远不返回的请求会一直占着一个工作线程——几个就够把线程池占满，
然后**整个 API 一起卡住**。

### 18.6 用本机 HTTP 服务补上"被桩掉的那一半"

第 1~9 组测试一口气把 `_download` 换成了桩，这是对的（一条外网请求都不发），
但代价是**真正的 httpx 调用一次都没被执行过**。而这里恰好有一条假设
是"我以为如此"而不是"我验证过"：

> `follow_redirects=False` 真的能让 httpx 不跟重定向吗？

如果它其实会跟（或者哪天版本升级改了默认值），那 §18.5 整段就是假的。
**这是整份测试里唯一一条"桩掉就永远发现不了"的漏洞。**

补法：起一个本机 `ThreadingHTTPServer`（不是外网），
`/redirect` 返回 302 指向 `/secret`，`/secret` 一被访问就记录。
然后**直接调 `_download`**（不经过任何桩），断言：

- 拿回来的是 302 而不是最终页
- **`/secret` 从来没有被请求过**

实测：httpx 的行为和假设一致。同一组测试顺带用真 socket 验证了
"到上限就停止读取"（服务端往连接里写三倍上限的字节，
客户端读回来的略多于上限、远小于三倍——证明 `break` 真的在起作用，
而不是先读完再判断大小）。

### 18.7 ★ 变异测试自己也会静默失效（一次假 GREEN）

**这是这一节里最值得讲的一段。**

把 `follow_redirects=False` 改成 `True`，跑一遍：**0 条测试变红。**

如果就此停手，结论会是"我的测试没覆盖这一条"——**而这是错的**。
真实原因是：`follow_redirects=False` 这个短串在文件里出现了**两次**，
第一次在函数的文档字符串里（第 371 行，解释这个参数为什么这么写），
第二次才是代码（第 377 行）。`replace(..., 1)` 改的是**注释**，
代码原封不动 —— 于是拿到一个假 GREEN。

把锚点换成带上周围代码的 `timeout=FETCH_TIMEOUT, follow_redirects=False`
再跑，`test_download_does_not_follow_redirects_by_itself` **立刻变红**。
测试一直是好的，坏的是验证测试的那个脚本。

| 变异 | 第一次结果 | 换锚点后 |
|---|---|---|
| `follow_redirects=False` → `True` | ★ 假 GREEN | **RED** ✅ |

**教训**：变异测试需要一个前提——"变异真的改动了行为"。
而这个前提本身也需要被检查。修法是两条硬约束：
锚点里带上周围代码，且**断言锚点在文件里只出现一次**。

同一批变异里还有一条幸存者（`cache_ignores_content_type_file`），
它**不是**假 GREEN，是**真的行为等价**：删掉 `meta.is_file()` 之后，
`read_text` 抛的 `FileNotFoundError` 正好被同一个 `except OSError` 接住，
结果碰巧一样。但它顺手指出了一个**真洞**——

> 类型文件存在但是**空的**（0 字节）能通过 `is_file()`，
> 于是缓存**命中**、并返回一个 `content_type=""` 的响应。
> 而"必须是 image/*"这条规则在缓存这条路径上**是不再检查的**
> （靠的是"进缓存的都过过闸门"这条不变量），空文件正是把不变量捅破的那个口子。

补上非空判断 + 一条测试，重跑变异确认变红。这条也写进了代码注释里，
连同"哪两个判断是冗余的、别把它们当成有测试兜底"的分工说明。

### 18.8 前端的四个决定

| 决定 | 理由 |
|---|---|
| 没有图时给**空占位**，不给破图图标也不给"暂无图片"四个字 | "没有图"在这一页是常态（Mock 一条都没有）；每行都出现一句提示，会盖过真正有图的那几行 |
| `imgFallback` 用 `function` 声明，**不能**写成 `const imgFallback = ...` | 它是给内联属性 `onerror="imgFallback(this)"` 调的，而内联属性里的名字从 **window** 上找。顶层 `const` 不会挂到 window 上——写成 const 的话图片一失败就是一个 ReferenceError，而界面只是"占位符没出来"，看不到报错来源 |
| 表格列数 `COL_COUNT` **从表头数出来**，不写死 | 空态和错误态的 `colspan` 写错不会报错，只会让内容不居中或把表撑宽。而"加一列"是这一页最容易发生、也最容易忘的改动——加缩略图这一列时刚刚发生过一次 |
| 原帖链接必须带 `rel="noopener noreferrer"` | 不带 `noopener` 的话，被打开的外部页面能通过 `window.opener` 把我们这一页导航走 |

另外，`/api/proxy-image` 是本项目**唯一一个不走 `apiRequest`** 的接口。
这不是遗漏：取图的是**浏览器的 `<img>` 加载器**，JS 根本插不进去，
所以它走不了；而它也因此天然拿不到 `?source=`——这件事本身也是对的，
取字节的动作和"这个平台的商品是什么样"无关。

### 18.9 这一阶段的遗留缺口（如实记录）

| 缺口 | 状态 |
|---|---|
| **没有浏览器端实测** | 本机没装 chromium（按计划它只是可选降级层）。缩略图的**观感**、`onerror` 兜底是否真的触发、`#m-figure` 在弹窗里的排版，全部没有经过人眼确认。这是这一节最大的裸区 |
| **真实取图没有联网实测** | 全部取图路径都由本机 HTTP 服务 + 桩覆盖，**没有对 `y.zdmimg.com` 发过一次真实请求**。理由是合规：SMZDM 侧请求已全部停止（见 §16）。所以"httpx 对着真实图床的表现"属于未验证 |
| 磁盘缓存**无上限** | 有意的取舍：单张图有 5MB 上限、数据源有限（100 个真实商品），最坏情况有界。加 LRU 要引入"何时过期、怎么并发清理"一整套逻辑。代码里写明了真上生产应该交给 CDN 或 nginx 的缓存层 |
| 前端语法检查依赖 node | `tests/test_frontend_scripts.py` 在没有 node 的机器上 **skip** 而不是 fail（"clone 下来能跑"的优先级高于"必须检查"）。所以它在别人机器上可能根本不跑 |
| 缓存没有"内容变了"的失效 | URL 里的图片被图床换掉时，本地缓存会一直返回旧图，直到手动 `?refresh=1`。图片 URL 里带日期和唯一 id，实际不会遇到——但这是个已知的、靠 URL 约定而不是机制保证的性质 |

## 十九、代码 review 全程记录（阶段 0–5 之后的实现审查）

到这里，计划里的六个阶段都落地了。接下来这一段时间做的是**另一种事**：

> 原话：**"标定过程和结论记进 docs/可行性评估.md，这是白捡的面试故事；
> 之后把评审重心切换到代码 review——计划的仗打完了，该打实现的仗了。"**

起点是一份 **18 条"可疑点"清单**（一次全库扫描 + 我自己读代码时记下的），
但那份清单上**每一条都只是怀疑**——没有一条被证实过。
所以这一节的价值不在"修了多少个 bug"，而在**怀疑变成结论（或者变成误报）
的那一套方法**，以及怀疑被证实之后暴露出来的**形状**。

全库测试：**696 → 765**（+69）。

### 19.1 这一轮的规矩

| 规矩 | 为什么 |
|---|---|
| **先复现，再修** | 清单是怀疑，不是结论。**复现不出来的按"未成立"记录**，不改代码（§19.3 就是一条） |
| **从上游推导，不手写清单** | 核对"接口有几个不支持 `?source=`"时，从 `app.openapi()` 的路径里数，而不是凭记忆列；核对归一化规则能不能命中的时候，拿真实归一化函数去跑，而不是读正则 |
| **变异测试要退回【真实的旧代码】** | `git show <上一个提交>:<文件> > <文件>`，而不是自己编一个坏版本。前者验的是"这些测试能不能抓住真实的旧代码"，后者只验"能不能抓住我临时编的那一个" |
| **红的必须恰好是预期的那几条** | 多红=测试之间有耦合，少红=有一条测试是假的 |

### 19.2 修掉的东西，按【形状】分组

| 形状 | 条目（括号里是实测数字） | 抓它的手段 |
|---|---|---|
| **承诺 > 实现** | `main.py` "唯一一个不接受 `?source=` 的接口"（实测是**十几个**，见 §19.3(4)）；`/docs` 顶部"统计接口都支持 `?source=`"（`/api/stats/sources` 就是不接受）；`worker.py` "初始化为 0 = 很久以前"（monotonic 的 0 是**开机时刻**，实测分界点精确在开机 300 秒）；`seed.py` 的报错信息指向别处 | **拿上游去核对写下来的话**：接口定义、归一化函数、时间函数的原点 |
| **先查后写**（并发） | 入队：4 个并发 → **4 个任务**，且每个请求都返回 200 + 新 id（没有一个认为自己被挡下）；建规则：4 个并发 → **4 条一模一样的规则**；改规则同洞第三处；认领任务——**误报**（见 §19.3） | 真实文件库（不是 conftest 的内存库）+ Barrier + 把语句之间的缝隙撑到 50ms |
| **分子分母口径不同** | "其他"店铺均价按**全部商品数**加权，而它的分子只来自有价的那些（正常形状 −0.13%，极端形状 **−9.61%**）；价格分布图的 `total` 是"**能进桶的**商品数"（smzdm：图上 85.7%，真实 84.0%） | 用一条**独立 SQL** 复算，不用手写常量比对 |
| **解析层是字符类，不是词典** | 两个字的单位只吃到一个字符：1千万 → **1000**（差 10⁴）、1万亿 → **10000**（差 10⁸）；`_CN_DIGITS` 缺"十"；`MODEL_SUFFIX_WORDS` 里的 `"pro+"` **永远命不中**（归一化先丢掉了 `+`） | 逐条构造只含该词的输入，跑**真实函数**，看它能不能活到比对那一步 |
| **参数能把数据删掉** | `seed --days 0`：退出码 1，而 mock 商品 **1000 → 0**、9 万条价格点消失（`--count 0` 同样）。修法分两道：CLI 退出码 2 + `seed()` 抛 ValueError，并把"生成"提到"删库"之前 | 在**真库快照**上跑一遍（用 `sqlite3.backup()` 取 WAL 一致快照，不能 `cp`） |
| **删不掉** | `products.suspected_duplicate_of` 是**自引用**外键：同一数据集里 `DELETE WHERE id=X` 报 `IntegrityError`，而 `DELETE WHERE source='smzdm'`（把指向者和被指者一起删）**成功**——SQLite 的立即外键在**语句结束时**判定，不是逐行 | 造一个"真实商品指着 mock 商品"的场景，再跑一次 `seed` |
| **缓存键漏字段** | 指纹白名单 8 个键，而模型看到的行有 **10** 个（少了 `platform` / `category`）→ 改了这两个字段缓存照样命中；prompt 里写"**全部商品**的价格直方图"，而直方图只装得下有价格的 | 拿"**模型实际收到的那一行**"去对照白名单，不看注释 |

**这张表和 §16.13 那张是同一个意思**：里面**没有一条是"某个模块算错了"**。
承诺 > 实现是**注释**的问题，先查后写是**并发语义**的问题，
口径不同是**两个都对的东西放在一起**才矛盾——它们在单模块的单元测试里
全都是绿的。

### 19.3 ★ 三条实测出来的"反直觉"

**(1) 三处竞态里有一处是误报——而那一处正是另外两处的样板。**

清单里怀疑 `claim_next_task`（认领任务）有同样的竞态。实测：真实文件库、
**120 轮 × 2 个 worker**（Barrier 让两条 UPDATE 尽可能同时发出），
**双赢 0 次、异常 0 次**。它本来就是"一条 SQL 完成选中 + 占住"，
而且除了内层子查询，外层还带了一次 `status='pending'` 做守卫。

于是修另外两处的方案不用另想——**照它写**。一份清单里 2 真 1 假，
假的那个不是白跑的：**不实测就不知道它能不能当样板**。

**(2) 我自己的修复里犯了同一个错误。**

改 `/docs` 那句"所有统计接口都支持 `?source=`"时，我第一版新文案写的是
"不接受这个参数的接口**只有两个**：`/api/stats/sources` 和 `/api/proxy-image`"
——**仍然是过强的断言**。是在写测试前先去把真实清单数出来（远不止两个）
才发现的。所以最后改成：不写"一共几个"，只陈述"本接口不接受"。

测试守的是其中**守得住的那部分**：`/api/stats/*` 这个子集里"除
`/api/stats/sources` 外都支持"（`test_the_docs_claim_about_source_filter_matches_the_actual_endpoints`，
它从路由表里数，不维护手写清单）。至于"全项目到底有几个不接受"，
最后**连数都不数了**——理由见下面第 (4) 条。

**"唯一""全都""永不""只有"是最该被核对的词**：它们读起来最强，
也最容易被写下来之后没人再验一次。这一轮里光是这一类就抓到四处。

**(3) "守门的函数"变成了"解释门为什么没开"——这是重构里最容易骗过 review 的动作。**

并发修复把判断塞进了写语句自己的 `WHERE` 里，于是
`_assert_not_duplicate` 不再做判定，只在**没写进去之后**复算原因、提供报错文案。
名字没变、调用点还在、测试也都还是绿的——但它从"防线"降级成了"说明"。
如果哪次重构把写语句里的 `~_duplicate_exists(...)` 弄丢了，
这个函数会**安静地退化成唯一的防线**，也就是退回原来的样子。

所以在它的 docstring 和文件顶部【2】都单独写明了这件事：
**这类"职责悄悄变了但形态没变"的改动，光看 diff 是看不出来的。**

**(4) ★ 上面那个数字，我在这一节里又写错了一次——交之前重数才发现。**

这一节初稿的表格里，我填的是"实测 **11 个**"。准备提交前顺手从
`app.openapi()` 里重数了一遍：**12 个**。同一份代码、同一个我，
差的那一个来自手工列举时看漏的一行。而这行数字**没有任何测试守着**——
上面那条测试只数 `/api/stats/*` 这个子集，其余端点它不管。

于是同一轮里发生了两次同形的事：**先是在 `/docs` 文案上，
然后在"记录这件事的那一节"里。** 第二次尤其说明问题——
那一节的题目正是"不要写没人核对过的强断言"，写它的过程本身照样会犯。

修法跟着变了：`app/main.py` 那段注释里**连数字都不写了**，
只陈述形状（"不止一个"），另加一条测试
（`test_proxy_image_is_not_the_only_endpoint_without_source_filter`）
钉住这个形状——断言 `/api/proxy-image` 确实在不接受 `?source=` 的集合里，
且集合**不止一个**。数字会随端点增减而变，钉住它等于每加一个接口
就要改一次测试；而"不止一个"才是我真正想保住的那个事实。

★ 顺带记一个取舍：那条测试的**第二个**断言（集合 > 1）**没有做变异验证**
——要让它变红得把十几个端点删到只剩一个，不具备可操作性，所以它是
"照事理写的、但没被红过一次"的守门语句。第一个断言做了：给
`/api/proxy-image` 临时加一个 `source` 参数，红的**恰好**是这一条
（`/api/stats/*` 那条照旧绿——它根本不看这个端点）。

### 19.5 这一节真正的产出

计划里那六个阶段证明了"这条链路能跑通"。
这一节证明的是另一件事：**跑通的链路里，错误不会以"报错"的形式出现。**

这一轮修掉的东西，按"有没有报错"分类：

- **报错的**：`seed --days 0`（退出码 1，但数据已经没了）、自引用外键（`IntegrityError`）——**两条**
- **不报错、只是数字不对的**：加权平均、价格分布的分母、两个字的单位、"十"、`pro+`
- **不报错、只是行为和承诺不一样的**：四处"承诺 > 实现"、指纹漏字段、prompt 说"全部商品"
- **不报错、只在并发下发生的**：入队与建规则的重复行

§19.2 那张表里的**七类、十七个条目**（其中一个是误报）中，
**只有两条会报错**——`seed --days 0` 的退出码，和自引用外键的
`IntegrityError`（分属两类：参数能删数据、删不掉）。而且第一条
还是"先把 1000 个商品删干净了、再报错退出"。

剩下的每一类、每一条，界面都正常、接口都返回 200、测试都是绿的——
**它们唯一能被发现的方式，是有人拿着"这东西应该是什么样"
去核对"它实际是什么样"**。

而那句话（"应该是什么样"）恰恰是写在注释、文档、prompt 和
`/docs` 顶部那些地方的东西。所以这一轮最实用的一个动作，
不是读代码，而是**读我们自己写下的承诺，然后去验它**。

### 19.6 补交付物时，同一个形状又出现了一次（这一次在一个 .bat 的 echo 里）

这一节写完、开始补 `README.md` 和 `启动服务.bat` 的时候，
脚本第一版的头部 `echo` 里写着：

```
2) 采集 worker —— 认领采集任务、每 5 分钟检查一次告警
```

而它启动 worker 用的命令是 `python -m scraper.worker --replay`。
**这两句对不上**：`--replay` 在 `main()` 里是一条"跑完就 `return 0`"的分支
（`scraper/worker.py` 的 `if args.replay is not None:`），
**根本不进轮询循环**——它既不认领任务，也不检查告警。

实测（临时库上入队一个 mock 任务 + 一个 smzdm 任务，跑默认参数的 `worker --once`）：

```
#1 mock   success  解析 100 条，新商品 45，归并 22，待核对 33，新增价格点 100
#2 smzdm  failed   未联网（不是被拦截）：SmzdmSource 默认不联网……
                   ★ 修法：加 --allow-network 走真网络，或加 --replay 走离线重放。
```

也就是说：**不带任何 flag** 的 worker 能认领并跑完任务，而且对 smzdm 任务
给出的失败信息是准确的、可操作的（这是 16.9 那次修正的成果）；
`--replay` 则打印完"重放完成"就退出。

★ 值得记的是这个形状**又一次换了地方**：

§19.2 那张表里，它出现在 Python 的注释、`/docs` 的说明、prompt 和文档里；
这一次它出现在**一个批处理脚本的 `echo` 里**——而这一整轮 review 从头到尾
没看过 `.bat`：它不在任何测试的覆盖范围内，也没有任何机制会去读它。
而这恰好是 §19.2 那段结论的又一次印证：

    **"承诺 > 实现"这个形状，与语言、与文件类型、与有没有测试都无关。**
    它只跟一件事有关——**有没有人拿那句话去对一遍现实。**

这一次对上，是因为写 README 的"快速开始"时要顺手跑一遍脚本里的命令。

修法：`启动服务.bat` 改成**不带 `--replay`** 启动 worker（这样头两句话才成立），
真需要灌真实数据时另开窗口跑 `--replay`，并在脚本里写明它是"灌一次就退出"；
README 的快速开始也照这个改（两处命令的语义差别写在各自旁边）。

### 19.7 补验：worker 被 kill -9 之后，任务到底会不会永远卡住

这是 18 条清单里唯一没有对应提交的一条（§19.4）——阶段 4 写的自愈代码和两条测试
都在，但**这一轮一直没有回去复现**。所以补做了一次，而且刻意用**真的杀掉进程**，
不是把 `updated_at` 改一下就当崩溃（那只是测试里已经做过的事）。

**做法**：临时文件库 → 入队一个 mock 任务 → worker 轮询模式跑起来 →
**紧轮询日志，一看到"认领任务"就 `kill -9`**。

**第一次打空了**：我在看到日志后又等了 1.5 秒才杀，结果任务在我杀之前就跑完了
（`success`，1000/1000，`解析 1000 条，新商品 76，归并 573，待核对 351`）。
—— mock 源是本地生成的，1000 条不到两秒。改成**看到那一行立刻杀**才打中。

**打中之后的实测链条**：

| 步骤 | 实测结果 |
|---|---|
| 崩溃瞬间 | 任务停在 `running`，`progress=0`，`total=None`，message = `已认领，正在抓取…` |
| 立刻看接口 | `stale = False`（**对的**：还没到 10 分钟）、`percent = None`（**对的**：total 未知 → 前端显示不确定态而不是 0%） |
| 把 `updated_at` 拨回 11 分钟前（**唯一的加速**——等满 10 分钟没有信息量） | `stale = True`，界面会显示"可能已中断" |
| 重启 worker | 日志打出 `有 1 个任务卡在 running，已打回 pending 重跑` → 随后 `认领任务 #1` → 跑完：`success`，1000/1000，`新商品 76，归并 573，待核对 351，新增价格点 1000` |

★ 结论：**这条从"未复核"改记为"已实测"**。三个组件（自愈、`stale` 判定、
`percent=None` 的不确定态）在一条时间线上各自做对了自己的那一份，
而且**崩溃重跑后的结果与不崩溃时完全一致**（两次都是 76 / 573 / 351 / 1000）
——Mock 输入是确定的（固定随机种子），重跑不会产生第二套数字。

★ 顺带记一条：这次"第一次打空"本身也是信息——它说明这个任务**比直觉快得多**
（1000 条 < 2 秒）。如果哪天真要用 `kill` 复现一个崩溃，等待时间得按实测来定，
不能按感觉定。这和 §19.1 那条"先复现再修"是同一件事的另一面：
**复现不出来的时候，先怀疑复现手法，再怀疑结论。**

### 19.8 补验：多进程（`uvicorn --workers 3`）下那个并发判断还成不成立

§19.4 里记着"多进程下同理（判断在语句里，不在进程里），但没有实测过"。
补做了一次，用的是**真·三个进程**：`uvicorn app.main:app --port 8002 --workers 3`，
数据库指向真库的 `backup()` 快照（不能 `cp`，§19 之前的教训）。

**实测结果**：

```
INFO:     Started parent process [53180]
INFO:     Started server process [54224] / [52724] / [53024]      ← 三个真进程

4 个并发 POST /api/tasks/crawl?source=smzdm：
  响应 1: id=1 status=pending notice=无      ← 新入队的那个
  响应 2: id=1 status=pending notice=有
  响应 3: id=1 status=pending notice=有
  响应 4: id=1 status=pending notice=有
库里 crawl_tasks 行数：1
日志里 database is locked / OperationalError / Traceback / 500：0 处
```

**★ 但这一次的证明力要如实说清楚**：窗口**没有撑开**（撑开要在引擎上挂监听器，
在真实 uvicorn 进程里做不到，而 patch 被测代码是不允许的）。所以它**不能替代**
`tests/test_concurrency.py` 里那次撑开窗口的复现。它验的是另外三件事：

1. Windows 上 `--workers N` 这个模式**能跑起来**（这点本身值得验，见下面的坑）；
2. 三个进程并发写同一个 SQLite 库**没有锁冲突**（`busy_timeout=30s` + WAL 生效）；
3. 判断确实**不依赖进程内状态**——如果防线是模块级的集合或锁，三个进程下必然漏。
   这一次恰好只写了 1 行，是这一条的证据。

**★ 顺带踩到两个运维细节，都值得记**：

- **supervisor 被杀之后，三个 worker 会变成孤儿继续服务。** 我第一次 `taskkill` 只杀了
  父进程 53180，结果 `netstat` 上 8002 仍在 LISTENING、`/api/health` 仍返回 200——
  服务根本没停。要停得**按三个子进程的 PID 分别杀**（或者用 `taskkill /T` 杀整棵树，
  但父进程没了之后 `/T` 也找不到它了）。**"关了服务"这件事在多进程模式下
  不能只看父进程。**
- **进程表里显示的是基础解释器的路径**（`E:\pycharm\PYTHEN\python.exe`），
  不是 venv 里那个 python。因为 uvicorn 的 `--workers` 在 Windows 上走
  `multiprocessing.spawn`，子进程是重新起解释器。它看着像"venv 没生效"，
  但导入是正常的（health 200、接口全部可用）——spawn 会把父进程的 `sys.path`
  带过去。**看见进程表就先下结论"环境不对"，会和真相差很远。**
