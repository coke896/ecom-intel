# 电商竞品情报分析平台 — 可行性评估

> 评估日期：2026-09-28
> 评估对象：原始需求文档（数据采集 / 清洗存储 / 可视化 / AI 分析 / 导出告警 / 进阶功能）

---

## 一、总体判断

**选题方向是对的**，理由：

- 数据采集 → 清洗 → 存储 → 可视化 → AI 分析 → 出口（导出/告警）是一条**完整闭环**，面试时能一口气讲 20 分钟不重复
- 每一环都有可深挖的技术决策点（见文末"面试亮点"），不是 CRUD 堆砌
- 与你已有的 aiwenda 项目（FastAPI + 智谱 GLM + SSE）技术栈重合，可以复用经验，学习成本低

**但是**，原方案里有 **3 个会导致项目烂尾的硬坑** 和 **2 个逻辑漏洞**。如果按原文照做，会在第 1 周就卡死在采集上，后面 4 个模块全部没时间做。

核心结论一句话：**把项目定位从"爬虫项目"改成"数据管道 + 分析项目"，采集只是入口，不是主体。**

## 二、三个硬坑

### 坑 1：1688 和淘宝是一家的（最严重）

原文说"别碰淘宝/京东的反爬，你搞不定"，这个判断完全正确 —— 但紧接着推荐 1688，这是个致命误判。

**1688 是阿里巴巴集团旗下的 B2B 平台**，和淘宝共用同一套风控体系（阿里系）：

| 反爬手段 | 说明 |
|---|---|
| 滑块验证码 | 阿里自研，行为轨迹检测，无头浏览器一样拦 |
| 请求签名 | `_m_h5_tk` / `sign` 参数由 JS 动态生成，需要完整逆向 |
| 登录态强依赖 | 商品详情、价格、销量大量内容登录后才可见 |
| 设备指纹 | Canvas / WebGL / 字体列表检测，Playwright 默认指纹会被识别 |

结论：**你会在 1688 上花掉 80% 的项目时间，且大概率抓不到稳定数据。** 难度和淘宝同级，不是"替代品"，是"同一个坑"。

→ 替代方案见 **第四节：数据源方案**

---

### 坑 2："Playwright 比 requests 稳" 这个说法是错的

准确的技术表述应该是：

| 数据所在位置 | 正确工具 | 原因 |
|---|---|---|
| XHR / JSON 接口 | `httpx` 直接请求接口 | 快 10–50 倍，稳定，无浏览器开销 |
| 服务端渲染的 HTML | `httpx` + `parsel`/`lxml` 解析 | 够用，轻量 |
| JS 客户端渲染 | Playwright | 只有这种情况才需要真浏览器 |
| 有反爬指纹检测 | Playwright + 指纹伪装 | 不得已才用 |

真实工程里是**分层降级**：

```
尝试解析 JSON 接口  ──失败──▶  尝试解析 HTML  ──失败──▶  Playwright 渲染
     (最快)                        (中等)                  (最慢，最后手段)
```

**面试时讲这个分层策略，比讲"我用了 Playwright"高一个档次。** 前者体现判断力，后者只是工具名。

**Playwright 的真实成本**（原文没提）：

- 一个 Chromium 实例占 **300–500 MB 内存**
- 并发 5 个 page 就 2 GB+，Windows 上很容易卡死或触发 OOM
- 必须用 `asyncio.Semaphore` 限制并发（建议 2–4 个）
- 启动开销约 1–3 秒/实例，所以要让 browser 常驻、只新建 context/page

### 坑 3：`BackgroundTasks` 不适合长任务

`BackgroundTasks` 的设计意图是"请求结束后顺手做点小事"（发一封邮件、写一条日志）。用它跑几分钟的爬取任务会出四个问题：

1. **阻塞服务**：同步任务会占用 uvicorn 的 worker 线程
2. **无进度反馈**：前端不知道爬到第几个商品了，只能干等
3. **无法取消**：用户点了"取消"，任务还在跑
4. **重启即蒸发**：服务一重启，所有进行中的任务消失

→ **替代：任务落库 + 独立 worker 进程**

```
API 收到采集请求
   └─▶ 往 task 表插一条记录（status=pending），立即返回 task_id
         └─▶ 独立 worker 进程轮询 task 表，取任务执行，实时更新 progress
               └─▶ 前端轮询 /api/tasks/{id} 拿进度
```

MVP 阶段用 SQLite 当队列就够，**不要上 Celery**（需要 Redis/RabbitMQ，对单机项目是过度设计）。面试话术：

> "我评估过 Celery，但引入 Redis 会增加部署复杂度，我的数据量是每天几千条、单机运行，用 SQLite 做任务队列 + 独立 worker 进程完全够用。这是有意识的取舍，而不是不会用 Celery。"

## 三、两个逻辑漏洞

### 漏洞 1：「价格趋势折线图」没有数据可画

原文写"价格趋势折线图（同一商品多次采集的价格变化）"—— 但如果你**今天才开始采集**，数据库里只有**一个时间点**的数据，折线图画出来是一个点。

趋势分析是这个项目的核心卖点之一，不能没有。三个替代方案（按推荐度）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 用现成历史价格** | SMZDM 的"好价"页面本身就带历史价格和发布时间 | 数据真实 | 覆盖商品有限 |
| **B. Mock 历史数据生成器** ⭐ | 写一个 seeder，按真实价格分布规律（随机游走 + 促销跳变）生成过去 90 天的价格序列 | 演示效果满分，可控，永远能跑 | 数据是模拟的 |
| **C. 时间压缩** | 定时任务改成 5 分钟一次，跑一上午就有几十个数据点 | 全真实 | 只能演示短期，且耗时间 |

**推荐 A + B 组合**：真实数据用 A，趋势演示用 B 补足。面试时如实说明："趋势功能的数据源是模拟生成的，用于验证分析 pipeline；真实采集部分我实现了完整的分层降级策略。" —— 诚实且专业，比含糊其辞强得多。

---

### 漏洞 2：「增量采集」的定义不成立

原文写"记录每个商品的 链接+最后采集时间，只更新有变化的或新增的商品"。

**问题：不重新抓取，你怎么知道有没有变化？** 这个描述在逻辑上无法实现。

正确的增量策略是**两个层面**，分开处理：

| 层面 | 策略 | 效果 |
|---|---|---|
| **列表页增量** | 抓到的商品链接，与数据库已有链接比对，只对**新增**的入库 | 这才是真正的"增量" |
| **详情页刷新** | 按 `last_crawled_at` 排序，只重抓超过 TTL（如 24 小时）的商品 | 这才是"只更新有变化的"的可行实现 |

伪代码：

```python
# 第一层：列表页只处理新链接
existing_urls = db.get_all_product_urls()
new_urls = [u for u in crawled_urls if u not in existing_urls]
# 第二层：老商品按 TTL 决定是否重抓
stale = db.query_products(last_crawled_before=now - timedelta(hours=24))
targets = new_urls + stale
```

面试时把这两层讲清楚，是明确的加分项 —— 说明你真的想过这个问题，而不是背概念。

**面试话术模板**：

对比"我爬了淘宝"（吹牛，面试官一问细节就露馅），这个话术的可信度和专业度高得多。

## 五、能够做、且值得做的部分

### ✅ 1. SQLite 表结构设计

完全可行，且是很好的展示点。建议表结构：

| 表名 | 用途 |
|---|---|
| `products` | 商品：标题、URL、当前价、销量、店铺 ID、`last_crawled_at` |
| `price_history` | 价格变动历史：商品 ID、价格、采集时间 |
| `shops` | 店铺：名称、平台、商品数 |
| `crawl_tasks` | 任务：状态、进度、开始/结束时间 |
| `alerts` | 告警规则与触发记录 |
| `analysis_reports` | AI 分析报告缓存（带数据指纹） |

**必须注意**：开 WAL 模式。

```sql
PRAGMA journal_mode=WAL;
```

原因：后台 worker 写入 + FastAPI 读取会争抢写锁。WAL 模式下读不阻塞写、写不阻塞读。**这个细节面试能聊。**

数据量评估：单机采集，每天几千条、累计几十万条以内，SQLite **完全够用**，不要上 PostgreSQL。

### ✅ 2. 数据清洗 —— 这是项目最值钱的部分

"已售1万+" → `10000` 这类脏数据解析，是**最能体现工程能力**的地方，因为它需要处理大量边界情况：

| 输入 | 期望输出 | 陷阱 |
|---|---|---|
| `已售1万+` | 10000 | |
| `1.2万` | 12000 | 小数 |
| `3千+` | 3000 | 中文单位 |
| `9999` | 9999 | 纯数字 |
| `暂无` / `--` | `None` | 空值，不能崩 |
| `券后199-299` | min=199, max=299 | 区间 |
| `￥199.00` | 199.0 | 货币符号 |

**必须写单元测试**，覆盖每一个边界情况。测试覆盖率是简历上的硬指标，也是面试官最可能追问的地方。

### ✅ 3. 可视化

| 图表 | 可行性 | 注意事项 |
|---|---|---|
| 价格分布柱状图 | ✅ 简单 | ECharts 直出，30 分钟 |
| 销量 Top20 排行 | ✅ 简单 | 横向柱状图更好看 |
| 店铺占比饼图 | ✅ 简单 | 超过 8 个分类要合并为"其他" |
| 折线趋势图 | ⚠️ | 见"漏洞 1"，需要先解决数据源 |
| **关键词词云** | ⚠️ 有坑 | 见下 |
| 表格分页 | ✅ | 后端 `limit/offset` |

**中文词云的坑**（原文没提）：

词云按空格切词，**中文必须先分词**，否则整个标题是一个词：

1. **分词**：用 `jieba`
2. **去停用词**：过滤"的、了、包邮、正品"等无意义词
3. **电商专有噪声**：过滤"旗舰店、官方、新款、正品、特价"等高频无意义词

这个处理流程本身就是一个模块，是很好的"数据清洗"素材。

---

### ✅ 4. GLM 智能分析 —— 可行且效果好

**Token 量核算**：50 个商品 × (标题 + 价格 + 销量 + 店铺名) ≈ 每个 50–80 tokens → 总计 **2500–4000 tokens**，GLM-4-Flash 上下文 128K，毫无压力。

**四个必须注意的点**：

1. **`temperature` 范围是 (0, 1)** —— 智谱的参数范围与 OpenAI 不同，传 1.5 会直接报错（你在 aiwenda 项目踩过这个坑）

2. **让它输出 JSON，而不是 Markdown**
   - ❌ "请输出一份 Markdown 报告" → 格式不可控，无法测试
   - ✅ "请按以下 JSON schema 输出" → 可控、可测试、可缓存、前端自由渲染

   ```json
   {
     "market_overview": {"price_bands": [], "main_selling_points": []},
     "pricing_strategy": {"findings": []},
     "consumer_concerns": {"top_concerns": []}
   }
   ```

3. **按数据指纹缓存，不按时间缓存**
   - 原文说"攒一批统一调一次"，方向对
   - 但更进一步：把分析结果按**输入数据的哈希**存入 `analysis_reports` 表。数据没变就命中缓存，一次 API 都不调。否则用户刷新一次页面就烧一次钱。
   - 面试话术："我用数据指纹做缓存键，而不是时间窗口 —— 因为同样的输入必须得到同样的缓存命中，否则缓存就没有意义。"

4. **模型选择**：`glm-4-flash` 免费额度足够开发全程，`glm-4-plus` 效果好但收费。开发用 flash，最终演示可切 plus。

`pandas.to_excel()` + `openpyxl`，十几行代码。注意：导出大数据量时用流式响应（`StreamingResponse`），不要把整个 DataFrame 塞内存。

### ✅ 6. 告警 —— 但"前端标记"不算告警

原文说"简单版：前端标记" —— **前端标记只是个筛选器，不是告警**。告警的定义是"用户不看着屏幕也能收到通知"。

**正确实现**：

```
后台定时任务检查价格 → 命中规则 → 写入 alerts 表 → 推送到外部渠道
```

**推送渠道建议**（按易用度排序）：

| 渠道 | 难度 | 说明 |
|---|---|---|
| **Server酱 / 企业微信机器人 / 钉钉机器人** ⭐ | ⭐ | 免费、国内直连、几行代码搞定，最适合演示 |
| 邮件 SMTP | ⭐⭐ | 容易进垃圾箱，需配置 SPF |
| Windows 桌面通知 | ⭐ | 只有本机能收到，适合本地 demo |

### ✅ 7. APScheduler 定时任务

可行。**两个坑**：

1. **默认的 `MemoryJobStore` 重启后任务全部丢失** → 用 `SQLAlchemyJobStore` 持久化，或者干脆自己写一个 `while True` + sleep 的调度循环（更可控、更好调试）
2. **必须加运行锁**：上一次采集没跑完，下一次又启动了，会导致重复采集和数据污染。用 `max_instances=1` 或数据库标志位

## 六、进阶功能的现实评估

### 图片采集 ⚠️ 有坑

**防盗链问题**：直接 `<img src="对方域名/xxx.jpg">` 大概率返回 **403**，因为服务器检查 `Referer` 头。

**替代方案**：

```
后端图片代理：/api/proxy-image?url=xxx
   └─▶ 服务端带正确的 Referer + UA 去请求
         └─▶ 转发给前端
```

或下载到本地 `data/images/`，数据库只存路径（**不要存 BLOB**）。

---

### 评论情感分析 ⚠️ 难度被严重低估

**评论是所有数据里反爬最狠的**，比商品列表难一个数量级：

- 京东 / 淘宝：评论接口需要登录态 + 签名
- SMZDM：相对松，但要翻页，且评论量有限

**替代方案**：

1. 用公开中文情感数据集（ChnSentiCorp、微博情感数据集）验证分析 pipeline
2. 只抓少量（几十条）真实评论，重点展示"清洗 → GLM 分析 → 结构化输出"的**流程完整性**

面试话术："数据源受限于合规和反爬，我用公开数据集验证了 pipeline 的效果，重点在于 prompt 设计和结果结构化。"

## 七、架构建议

```
ecom-intel/
├── backend/              # FastAPI 应用
│   ├── main.py
│   ├── api/              # 路由层
│   ├── db/               # SQLAlchemy 模型 + 会话管理
│   └── services/         # 业务逻辑
├── scraper/              # 采集层（可独立运行）
│   ├── sources/          # 每个站点一个 adapter（smzdm.py / mock.py）
│   ├── pipeline/         # 清洗、去重、增量判断
│   └── worker.py         # 独立 worker 进程
├── analysis/             # GLM 分析
│   ├── prompts/          # prompt 模板
│   └── reporter.py       # 报告生成 + 缓存
├── frontend/             # 静态页 / Vue
├── data/                 # SQLite + 图片
│   └── images/
├── tests/                # 单元测试（清洗函数必须覆盖）
└── docs/
```

**关键设计原则：采集层独立于 Web 层。**

- 采集器可以 `python -m scraper.worker` 单独跑（调试方便）
- 也可以被 API 触发（入队）
- **这个解耦是面试重点** —— 说明你懂"关注点分离"

## 十二、真实数据标定实录（开工后的实测发现）

> 本节记录的是**计划付诸实施后**、在真实 SMZDM 页面上实测到的情况。
> 与前十节（纸上评估）不同，这一节的每个数字都来自实际抓下来的数据。
>
> 保留这一节的原因：**它是本项目最有说服力的面试素材**——
> 因为它展示的不是"我用了什么技术"，而是"我用数据推翻了自己的设计"。

### 12.1 采集侧：WAF 升级与主动停手

`/jingxuan/` 前 5 页抓取正常（HTTP 200、服务端渲染、结构完整），但在累计约
50–100 次请求后，服务端行为发生变化：

| 阶段 | 现象 |
|---|---|
| 正常期 | HTTP 200，约 380 KB 完整 HTML，可正常解析 |
| 升级期 | HTTP 200，**但响应体只有 1681 字节**，内容是腾讯验证码（TCaptcha）的 JS 挑战页 |
| 拦截期 | 全部端点 **HTTP 403** |

响应体里的特征字符串（`seqid` 变量、`TCaptcha.js` 引用）确认了这是
**WAF 的验证码挑战**，而不是页面改版或网络故障。

**处理方式：立即停止对 SMZDM 的请求，不做任何绕过尝试。**

理由有两层：

1. **合规层**：绕过验证码是明确越界的行为。本项目的定位是"学习研究用途的
   数据管道演示"，不是"突破访问控制"。这条线一旦跨过，项目性质就变了。
2. **工程层**：即便绕过成功，**这正是"采集层不可靠"的最好证据**——
   把系统建立在一个随时会被封的通道上，本身就是设计缺陷。
   正确的应对是让系统在**没有实时采集**的情况下仍然完整可用。

**由此产生的设计决策：离线夹具回放。**

把已验证的 HTML 落盘到 `spike/_raw/`（10.3 MB，26 个文件），
标定脚本默认离线运行，需要联网时才显式加 `--fetch`：

```python
OFFLINE = "--fetch" not in sys.argv
```

这不是权宜之计，而是一个正经的工程模式：
**测试和标定不应该依赖外部服务的可用性**。CI 里跑不了的东西不算测试。

### 12.2 数据源侧：双源策略

| 端点 | 实测结果 | 用途 |
|---|---|---|
| `search.smzdm.com` | HTTP 202 + `X-WAF-UUID` | ❌ 不可用 |
| `/fenlei/3cjiadian` | robots.txt **明确禁止** | ❌ 不抓 |
| `/fenlei/<其他 slug>` | HTTP 200 | ✅ 品类覆盖 |
| `/jingxuan/` | HTTP 200，服务端渲染 | ✅ 管道验证 |

**两个必须记下来的坑：**

1. **`/fenlei/` 的 slug 不是可靠的品类过滤器。** 实测三个不同 slug 返回的
   商品集合**字节级相同**——说明该路径的参数对内容没有实际约束力。
   不能据此声称"按品类精确采集"。
2. **`/fenlei/` 分页无效。** 翻页返回同一批内容。所以品类覆盖只能靠
   多个 slug 分别抓一次，不能靠翻页深化。

**最终策略**：`/jingxuan/` 用于**管道验证**（分页、时间戳、事件归并语义），
`/fenlei/<slug>` 用于**品类覆盖**（约 100 条配件商品）。两个来源在库中
用 `source_channel` 字段区分——因为两条通道的**记录时间语义不同**
（精选页的 `timesort` 是爆料发布时间，类目页没有这个语义）。

### 12.3 清洗侧：真实价格格式的分布

从真实页面提取的 543 个价格样本，格式分布如下：

| 格式 | 出现次数 | 说明 |
|---|---|---|
| `N元` | 217 | 普通价格 |
| `N元（需用券）` | 171 | 券后价 |
| `暂无报价` | 67 | 脏数据 → `(None, None)` |
| `N元起` | 50 | 开区间 → `(N, None)` |
| `N元（需买N件，需用券）` | 20 | **件数干扰** |
| `N元（淘金币可抵N元起）` | 17 | **抵扣额干扰** |
| `评论打卡瓜分N万积分！` | 1 | **促销 banner 文本，不是价格** |

**三个"第二个数字"陷阱**（这一条最有价值，因为朴素实现会全部中招）：

| 输入 | 朴素实现的结果 | 正确结果 |
|---|---|---|
| `193元（淘金币可抵0.97元起）` | `(0.97, None)` —— 取 min 或"元起"规则 | `(193, 193)` |
| `18.5元（需买3件，共55.5元）` | `55.5` —— 取最后一个数字，**虚高 3 倍** | `(18.5, 18.5)` |
| `8.01元（需买2件，需用券）` | `2` —— 取最小数字 | `(8.01, 8.01)` |

**结论：价格 = 第一个「数字+元」，而不是最大/最小/最后一个数字。**
括号里的内容全是**成交条件**，不是价格本身。

这条规则最终被实现为**优先级分流**（带单位区间 → 第一个"数字+元" →
裸区间 → 货币符号），并有 5 个真实用例守护（`test_parse_price_multi_number_traps`）。

### 12.4 ★ 归并阈值标定：一次被数据推翻的设计

**这是本节的核心，也是整个项目最有价值的工程决策。**

#### 背景

把 `/jingxuan/` 抓来的东西存进库后，会撞上一个语义问题：
**抓到的每一条不是"商品"，而是"爆料"（价格事件）。**
同一商品被反复爆料会产生多条记录，而"价格趋势图"需要的是每个商品的
价格时间序列。

所以需要一个**事件归并**逻辑：新爆料进来时，判断它属于哪个已有商品。

原始设计是两层：

```
硬门槛（品牌 + 规格 token） ── 一票否决
     ↓ 通过
软门槛（Dice ≥ 0.75）      ── 判定是否同一商品
```

**软门槛负责"判定"这个定位，是错的。** 下面是推翻它的过程。

#### 方法

1. 抓取真实标题，去重后得到 **277 条**（其中 51 条属于数码配件品类）
2. 消除**所有**先验假设，纯粹用数据说话
3. 人工逐对标注：**11 对**标题，判定"是不是同一款商品（SKU 层面）"
4. 计算三种相似度指标，看真阳性和假阳性能否被分开

> ★ **方法上的一个自我纠正**：第一版标注脚本用**模糊匹配**把标注文本
> 映射到语料标题，结果选错了标题，算出的分数和手算对不上。
> 改成**精确锚定**（命中 0 条或 1 条以上直接报错退出）后才得到可信结论。
> **测试脚手架自己出错比没有测试更危险**——它会给出错误的安全感。

#### 结果：三种指标全部不可分

| 标签 | 包含度 | Dice | Jaccard | 标题对 |
|---|---|---|---|---|
| 同款 | 0.750 | 0.545 | 0.375 | `FreeClip 2 …冰莓紫 Type-C` / `FreeClip 2 耳夹式耳机` |
| 同款 | 0.800 | 0.667 | 0.500 | `FreeClip 2 …Type-C` / `freeclip2 …冰莓紫` |
| 同款 | 0.667 | 0.533 | 0.364 | `Pura X Max 12GB+256GB` / `HUAWEI 华为 Pura X Max 手机` |
| 同款 | 1.000 | 1.000 | 1.000 | `百亿补贴：酷态科 充电宝10号…` / `酷态科 充电宝10号…` |
| **不同** | **0.857** | **0.706** | 0.545 | `iPhone 18 Pro Max …256GB` / `iPhone 18 Pro` |
| **不同** | **0.833** | **0.769** | **0.625** | `iPhone 18 Pro` / `iPhone Duo` |
| 不同 | 0.500 | 0.500 | 0.333 | `FreeClip 2` / `FreeClip 开放式设计`（一代） |
| 不同 | 0.500 | 0.400 | 0.250 | `酷态科 10号` / `酷态科 CP13` |
| 不同 | 0.500 | 0.444 | 0.286 | `斯凯奇 …女士跑鞋` / `斯凯奇 …男士健步鞋` |
| 不同 | 0.500 | 0.500 | 0.333 | `米良品 拖轮购物车` / `米良品 掏耳神器` |

**汇总判定：**

| 指标 | 真阳性最低 | 假阳性最高 | 结论 |
|---|---|---|---|
| 包含度 | 0.667 | **0.857** | ❌ 不可分 |
| Dice | 0.533 | **0.769** | ❌ 不可分 |
| Jaccard | 0.364 | **0.625** | ❌ 不可分 |

**三种指标全部不可分。** 任何单一阈值都无法同时收下全部真阳性、
排除全部假阳性。

最致命的是这一对：

```
Apple 苹果 iPhone 18 Pro 5G手机    ← 不同商品
Apple 苹果 iPhone Duo 5G手机       ← Dice 0.769 / 包含度 0.833
```

它的分数**高过四个真阳性中的三个**。如果归并决策交给相似度阈值，
这一对必然被错误合并，于是 `iPhone 18 Pro` 的价格序列里混进了
`iPhone Duo` 的价格——**而且不会报错，分析结论静默失真**。

> 直观原因：中文电商短标题清洗后通常只有 **4–7 个 token**，
> 在这个量级上，集合指标的取值是**离散且跳跃的**——
> 差一个词就从 1.0 掉到 0.5。信息量不足以支撑"同一商品判定"这么细的任务。

#### 转折：真正干活的不是相似度

回头审视那对最危险的假阳性，发现它有个特征：

| 标题 | 型号 token |
|---|---|
| `iPhone 18 Pro` | `{18, pro}` |
| `iPhone Duo` | `{duo}` |

**不相等。** 而所有真阳性对的型号 token 都是相等的：

| 标题对 | 型号 token |
|---|---|
| `FreeClip 2 …` / `FreeClip 2 …` | `{2}` / `{2}` ✅ |
| `freeclip2` / `FreeClip 2` | `{2}` / `{2}` ✅（修复后） |
| `酷态科 10号` / `酷态科 10号` | `{10, 10000毫安}` / 同 ✅ |
| `iPhone 18 Pro` / `iPhone Duo` | `{18, pro}` / `{duo}` ❌ 拦下 |
| `酷态科 10号` / `酷态科 CP13` | `{10}` / `{13}` ❌ 拦下 |
| `FreeClip 2` / `FreeClip`(一代) | `{2}` / `{}` ❌ 拦下 |

**型号 token 相等是必要条件，而相似度不是。**

#### 修正后的设计

```
新爆料
  └─▶ 归一化（去促销噪声、字母数字边界切分、★保留规格 token）
        └─▶ 【第一层 确定性规则】负责【排除】，不负责确认
              · 品牌必须相容（提取不出 → 视为通过，"无证据不否决"）
              · 型号 token 必须【严格相等】
              ├─ 不相等 → 绝不自动合并
              │    └─ 但若包含度 ≥ 0.75 → 标记待人工核对（不是静默丢弃）
              └─ 相等 → 进入第二层
                    └─▶ 【第二层 相似度确认】只负责【确认】
                          · 包含度 = |A∩B| / min(|A|,|B|)
                          ├─ ≥ 0.75        → 自动归并
                          ├─ 0.50 ~ 0.75   → 新建 + 标记 suspected_duplicate_of
                          └─ < 0.50        → 新建，不标记
```

**两层的分工是有讲究的**：
确定性规则可以证明"**不是同一个**"，但证明不了"是同一个"
（品牌型号都对也可能只是同系列）；相似度可以提示"**可能是同一个**"，
但不足以单独下结论。让两者各做擅长的事。

#### 修正后的效果（同一批 11 对标注）

| 指标 | 值 |
|---|---|
| 真阳性 TP | 3（正确归并） |
| 真阴性 TN | 7（正确分开） |
| **假阳性 FP** | **0**（零错归并） |
| 假阴性 FN | 1（漏归并，且被标记） |

**加上硬门槛后，通过门槛的 5 对里：需要拒绝的最高 0.500，
需要接受的最低 0.750 → 阈值区间 `[0.500, 0.750]`，完全可分。**

```
★ 核心结论：三种相似度指标全部不可分，加上类型门槛立刻可分
指标          真阳性最低   假阳性最高
包含度            0.667      0.857   ★ 不可分 ❌
Dice             0.533      0.769   ★ 不可分 ❌
Jaccard          0.364      0.625   ★ 不可分 ❌
--- 加上硬门槛后（只看通过型号门槛的 5 对）---
包含度            0.750      0.500   可分 ✅
```

#### 标定过程中额外发现的两个真 bug

| 现象 | 根因 | 修复 |
|---|---|---|
| `FreeClip 2`（带空格）与 `freeclip2`（不带）被判为不同商品 | 型号 token 分别是 `{2}` 和 `{freeclip2}` | 归一化时在**字母数字边界插入空格**（`freeclip2` → `freeclip 2`） |
| `iPhone 18 Pro` 与 `iPhone 18 Pro Max` 型号集相同 | `Pro`/`Max` 是纯字母，"提取含数字的 token"这条朴素规则抓不到 | 增加**型号后缀词表**（`pro`/`max`/`plus`/`ultra`/`青春版`…） |

两个 bug 都是**用真实数据标定才暴露的**——自己编测试用例时，
只会想到自己知道的情况。

#### 主动接受的代价

严格相等会**漏掉**"长标题带规格 vs 短标题不带规格"的同款，例如：

```
华为 Pura X Max 12GB+256GB 橄榄金…   型号 token {max, 12, gb, 256}
HUAWEI 华为 Pura X Max 手机          型号 token {max}
                                 → 不相等 → 漏归并
```

标定中试过放宽成"一个是另一个的子集"，结果 `iPhone 18 Pro`
`{18, pro}` 与 `iPhone 18 Pro Max …256GB` `{18, pro, max, 256, gb}`
会被判为相容——**但它们是两个 SKU**。

**这个代价是主动接受的**：

- 漏归并 → 只是少几个价格点，且会被标记进人工核对队列，**可恢复**
- 错归并 → 价格序列里混进别的商品的价格，**静默失真，不可发现**

两害相权，取保守的那个。这条取舍被写进了
`tests/test_dedup.py::test_known_cost_of_strict_equality`，
不允许后来者"优化"掉而不自知。

#### 局限的诚实说明

- 标注集只有 11 对。样本量小，阈值 `[0.500, 0.750]` 的区间宽度是**测出来的**
  而不是**推导出来的**，真实生产中应随采集天数增加再校准一次。
- 单次快照里"同一商品被多次爆料"的正样本天然稀少（**这正是要解决的问题本身**），
  所以正样本主要来自"规格相同、措辞不同"的标题对。
  真实生产中正样本会随采集天数累积变多。
- 11 对里有 2 对是"通过门槛但落进灰色地带"的假阳性
  （斯凯奇、米良品），它们会被标记但不会被合并——
  **灰色地带的精确率约 33%**。这是可接受的：核对队列本来就该以召回为先，
  代价只是人扫一眼。

这些局限如实写在这里，不假装标定是完美的。

### 12.5 这一节的复用价值

这套标定方法可以直接迁移到任何"短文本实体归并"场景
（商品去重、新闻事件聚合、工单合并）。它的核心不是某项技术，而是三条原则：

1. **先用数据验证指标本身，再谈阈值。** 我们花了半天证明"三种常用相似度
   指标在这个数据上不可分"，这半天的价值高于调参一周——
   因为它避免了把系统建立在一个**根本无效的信号**上。
2. **确定性规则负责排除，概率信号负责确认，不要反过来。**
   反过来用的后果是"看起来相似但确实不同"的样本被静默吞掉。
3. **把取舍和代价写进测试。** 漏归并是可接受的、错归并不是——
   这个判断必须固化成 `test_never_merges_dangerous_pairs`，
   否则下一个改代码的人（包括三个月后的自己）会把它"优化"掉。

## 十三、Mock 数据生成的三个实测发现

第十二节记的是**真实数据**上的标定。这一节记的是**合成数据**上的踩坑，
两者是不同性质的工作，但教训同源：**统计指标正常 ≠ 数据是对的**。

### 13.1 本文档第 107 行的建议是错的：不能用随机游走

第 107 行（早期方案）写的是：

> 按真实价格分布规律（**随机游走** + 促销跳变）生成过去 90 天的价格序列

实现时照着写成了 `p[t] = p[t-1] * (1 + ε)`，日波动 σ=0.012。
**实测 90 天后价格中位数跌到初始值的 12%**——折线图是一条一路下滑的滑梯。

原因是乘性误差会累积：`(1+ε)` 连乘 90 次，其对数是一个方差随时间线性增长的
随机游走，于是价格在对数空间里"走远了"。

正确做法：**所有价格围绕一个固定的 base 波动**，绝不围绕前一天累乘。

```python
错： p[t] = p[t-1] * (1 + ε)      # 对数漂移
对： p[t] = base   * (1 + ε)      # 永远在 base 附近，促销后自然回归
```

> **面试可讲**：这条建议是我自己写的方案文档里的，实现时才发现是错的。
> 更值得讲的是**判别方式**——所有统计指标（中位数、量级、无负值）当时都是"正常"的，
> 是画成图一眼看出来的。所以我后来把"画图"从"演示素材"改成了
> **开发期自检工具**，`spike/plot_seed.py` 的三张图和测试是同等地位的东西。

> 补充一点：直觉上会去断言"末价/首价的**均值**≈1"来判断有没有漂移。
> 这条对两种实现**都成立**——随机游走在对数空间近似对称，N 条路径的均值照样是 1，
> 只是每条路径各走各的。真正的判别式是**离散度**：
> 正确实现下 80 条序列的中位数 max/min < 1.1，累乘实现会到几倍。
> 见 `tests/test_seed.py::test_no_compounding_drift`。

### 13.2 大促日会被普通促销"吃掉"（而测试一直是绿的）

设计意图：第 30 天和第 75 天是全品类大促（模拟 618 / 双11），
让阶段③ 的 GLM 能检出"这两天有全品类价格低谷"——这是给 AI 出的考卷，
答得出来才说明它真在读数据。

原实现把大促判定写在了 `if promo_left == 0:` **内部**：

```python
if promo_left == 0:                    # ← 普通促销进行中时，整个分支不执行
    if t in BIG_PROMO_DAYS:            # ← 大促被跳过
        ...
```

于是当第 30 天正好落在一次普通促销中间（概率约 17%）时，大促**根本不发生**。
两个大促日合计，约 **30% 的商品缺至少一个大促**。

★ 关键在于：**有一个测试一直在跑，而且一直通过**。
它断言的是"200 个商品的日均值在大促日更低"——70% 的商品是对的，
取平均就把 30% 的缺失抹平了。

是价格曲线图暴露的：图上有几个商品第 30 天压根没有低谷。

修法：大促判断移到 `promo_left == 0` 之外，**无条件覆盖**正在进行的促销
（现实里也确实是这个语义——618 开始，日常促销就被盖掉了）。

> **面试可讲**：这是"**聚合指标掩盖个体差异**"的教科书案例。
> 凡是设计意图里带**全称量词**的（"全品类""每个商品都""所有接口"），
> 断言就必须落在个体上，不能落在均值上。
> 补强的 `test_every_single_product_has_the_big_promo` 是逐商品检查的，
> 修复前报出 7/240 缺失。

### 13.3 图会骗人：15 字截断让三个不同 SKU 看起来像"同一商品记了三次"

销量 Top20 图上出现了三条看起来一模一样的条形：

```
绿联 磁吸手机指环扣 金属 …     45,794
绿联 磁吸手机指环扣 金属 …      7,595
绿联 磁吸手机指环扣 金属 …      7,022
```

第一反应是"数据严重错误：同一个商品被记了三次，销量还不一样"。
查库才发现 Top20 里 **19 个标题都是唯一的**——那三条是**不同颜色的 SKU**
（深空灰 / 黑色 / 白色），而颜色恰好是标题的最后两个字，被 `t[:14]` 切掉了。

**数据没错，是图在骗人。** 按字符数截断对中文天然不公平：
15 个中文字占的宽度约为 15 个英文字母的 1.8 倍；
而"数码配件"品类的标题恰好是「品牌中文 + 型号英文 + 规格 + 颜色」，
最需要保留的颜色和规格都在尾部。

修法：按**显示宽度**截断（中文算 2、ASCII 算 1），
见 `spike/plot_seed.py::elide`。

> **面试可讲**：我先怀疑数据，查完才确认是呈现层的问题。
> 这个顺序是对的——但值得说出来的是**查证过程本身**：
> 发现"三个一样的标题销量差 6 倍"时，第一反应应该是去数据库核对，
> 而不是直接改图。如果反过来（先改图让它"好看点"），
> 就正好掩盖了一个可能真实存在的数据 bug。

### 13.4 三个发现共同的方法论

| 发现 | 统计指标 | 谁发现的 | 根因 |
|---|---|---|---|
| 累乘漂移 | 全部"正常" | 价格曲线图 | 对数随机游走 |
| 大促被跳过 | 均值断言通过 | 价格曲线图 | 分支嵌套位置错误 |
| 标签截断 | 数据本身没问题 | 看图起疑 → 查库 | 中英文宽度不等 |

三次都是**先看图**。所以 `docs/charts/` 里的三张图不是 README 的装饰，
而是和 `pytest` 并列的验证手段——这也是为什么 matplotlib 被列进
`requirements.txt` 的**硬依赖**而不是 dev 依赖。

## 十四、API 层的四个实测发现（阶段 2）

阶段 2 写完了 6 个统计接口 + 2 个商品接口，配套 69 个新测试
（`test_textutil.py` 26 个 + `test_api_smoke.py` 43 个），全库 281 个测试全绿。

这一节记录的是**测试和机械验证抓出来的四个问题**——
其中三个是代码 bug，第四个推翻了我自己在阶段 1 写下的一个"修复"。

### 14.1 空状态契约：同一个判断，写了两遍，漏了一遍

这个项目的 API 有一条自我约束：**「空」和「错」是两件事，而且空必须解释自己为什么空**。
`?source=smzdm` 下销量图没有数据，这不是 404、不是 500，
而是 200 + 空数组 + 一句"真实电商不公开销量"。

问题出在**有两条不同的空**：

| 情况 | 正确的话 |
|---|---|
| 这个数据源一条商品都没有 | "该数据源暂无数据（尚未采集）" |
| 有商品，但这个数据源没有销量字段 | "该数据源不提供销量数据（真实电商不公开）" |

第一版我把这个判断写在了 `overview()` 里，写对了。
`sales_top()` 里只检查了"有没有销量"，于是 **`?source=smzdm` 走进来会得到第二句话——
而那个数据源其实一条商品都没有**。测试 `test_empty_source_says_there_is_no_data_not_no_sales`
把它抓了出来。

修法不是再抄一遍判断，而是抽成 `_empty_notice(product_count)`：

```python
def _empty_notice(product_count: int) -> str:
    return SALES_UNAVAILABLE_NOTICE if product_count > 0 else NO_DATA_NOTICE
```

> **面试可讲**：这条规则我在两个地方实现了两遍，漏了一处。
> 真正该记住的不是"要小心别漏"，而是**同一个判断出现第二次时就该抽出来**——
> 漏掉的地方永远不会是自己以为写全了的那个。

同一类问题还有一个更隐蔽的版本：`PriceDistributionOut` **压根没有 `notice` 字段**。
前四个接口我都记得加，唯独价格分布忘了——它的空响应是 `buckets: []` 且没有任何解释，
前端只能显示"暂无数据"，**而"为什么没有"这个信息在接口层就丢了**。
补字段的时候我顺手加了一条测试：**一次性遍历全部五个空响应接口**，
断言每一个都带了非空的 `notice`。漏掉第六个接口的可能性依然存在，
但至少新增接口时会被这条测试拦住。

### 14.2 `elide_middle` 的差一错误（budget=2）

截断函数在预算极小的时候会返回 `'a…a'`——**显示宽度 3，超过预算 2**。
原因是 `max(1, ...)` 给头和尾各保底 1 个单位，再加上省略号本身就 3 了。

参数化测试 `test_result_never_exceeds_budget` 覆盖了 2/3/4/5/10/20/26/40 各档，
只有 budget=2 炸。修法是加一个早退分支：**尾巴拿走全部预算**。

```python
if avail < 2:
    return "…" + _take_tail(text, avail)
```

同一轮里还有第二个顺序问题：**"放得下就原样返回"的判断必须排在预算守卫之前**，
否则 `budget <= 0` 的早退会先把正常输入也一起吃掉。

> **面试可讲**：这个 bug 之所以能被抓到，是因为**测试是参数化的而不是举了几个例子**。
> 我手写用例的话会写 budget=20、budget=26，绝不会写 budget=2——
> 而边界恰恰只在参数空间的角落上。

### 14.3 ★ 证伪：`title_short` 那个"修复"根本不成立

这是本阶段最有价值的一个发现，因为**它推翻的是我自己在阶段 1 留下的结论**。

背景见 §13.3：销量 Top20 图里三个不同颜色的 SKU 看起来像同一个商品，
因为按字符数截断把标题尾部的颜色切掉了。阶段 1 的修法是
**改成按显示宽度截断，并且保留尾部**（中文算 2、ASCII 算 1，头部 60% + 尾部 40%）。

阶段 2 把这段逻辑搬进 `app/textutil.py` 并补测试时，我写了一条测试：

> 三个只差颜色的 SKU，截断后必须仍然长得不一样。

**它没过。**

我以为是预算选小了，于是把阈值从 26 调到 30、再到 40，逐个实测：

| 预算 | 三个 SKU 的 `title_short` | 可区分？ |
|---|---|---|
| 26 | 三个完全相同 | ❌ |
| 30 | 三个完全相同 | ❌ |
| 40 | 三个完全相同 | ❌ |
| 60 | 三个都是完整原文，彼此不同 | ✅ |

去看那条标题的实际结构才明白：

```
绿联 磁吸手机指环扣 金属 超薄 深空灰 商务款 送礼佳品
```

颜色（`深空灰`）在**第 5 个 token**，后面**还跟着 2 个纯营销 token**。
"保留尾部"保留下来的是"商务款 送礼佳品"——**恰好是信息量为零的那部分**。
预算 60 之所以"能区分"，是因为 60 已经大于标题本身，等于没截断。

结论不是"把预算调到 60"，而是：**任何固定的截断策略都无法保证不同 SKU 一定长得不一样。**
保留尾部在颜色靠后时有用，在颜色靠前、营销语靠后时就是有害的；
调大预算只是让它退化成"不截断"，那图例就放不下了。

**真正的修法是换一层解决：图例只负责放得下，完整标题交给 tooltip。**
`app/textutil.py` 的模块 docstring 现在写着这张实测表格和上面那句结论；
`charts.js` 的 `renderSalesTop` 在 tooltip 的 formatter 里用的是完整 `it.title`。

对应的测试也从一条改成了两条：
一条断言"工具提示必须拿到完整标题"（这是真正要保证的契约），
另一条断言"截断在预算内且带省略号"（这是排版约束），
**而"不同 SKU 必须可区分"这条被我删掉了——因为它做不到，留着就是一条假承诺。**

> **面试可讲**：这条最有价值的地方是**测试推翻了我自己的修复**。
> 阶段 1 我以为"改成按宽度截断 + 保留尾部"就解决了，
> 阶段 2 补测试时才发现它只是把问题从"颜色被切掉"变成了"颜色被营销语顶掉"。
>
> 而且这里有个陷阱：**如果我把预算直接调到 60，测试会变绿**，
> 然后我会以为自己修好了——实际上只是绕开了。
> 所以值得说的是那个"我准备调参数，先停下来量了一下"的动作：
> 量完发现**26/30/40 三个档位的结果一模一样**，
> 那就说明这不是"调得不够大"，而是**策略本身不对**。

### 14.4 一个被自己写错的断言：25 是合法的分桶步长

价格分布的分桶用的是"好看的步长阶梯"：
`(5, 10, 20, 25, 50, 100, 200, 250, 500, 1000, 2000, 2500, 5000)`。

测试里我写的是 `assert step % 10 == 0`，结果真实数据算出来的步长是 **25**，测试红了。

**是我测试写错了**：25 就在我自己列的阶梯里，是我写断言时想当然地
把"好看的步长"理解成了"10 的倍数"。

改成 `assert step in GOOD_STEPS` ——**断言应该检查它真正依赖的那个性质**，
而不是一个碰巧在多数情况下等价的近似。

> **面试可讲**：这个错误很小，但它和 §14.1 是同一类：
> **规则应该只有一处定义**。步长阶梯是个常量元组，
> 断言却不引用它、而是重新描述了一遍"什么算好步长"，
> 于是两份描述对不上时，我第一个怀疑的是代码而不是测试。

### 14.5 四个发现的方法论

| 发现 | 抓它的手段 | 根因 | 性质 |
|---|---|---|---|
| 空状态文案用错 | 单测（分阶段灌数据） | 同一判断写了两遍 | 代码 bug |
| `PriceDistributionOut` 缺 `notice` | 单测（遍历全部接口） | 规则覆盖不全 | 代码 bug |
| `elide_middle` 超预算 | 参数化单测 | 边界差一 | 代码 bug |
| `title_short` 策略不成立 | 单测 → 实测标定 | **假设错了** | 设计缺陷 |
| 步长断言过严 | 单测 | 规则描述了两遍 | 测试 bug |

前三条是"代码没实现好"，第四条是"想法本身不对"，第五条是"检查方式不对"。
四者混在一起时最容易的反应是**全都当代码 bug 改**——
而第四条那样改，只会把问题藏起来。

### 14.6 一条没能验证的验证点（如实记录）

阶段 2 计划里的验证点是：

> `?source=mock` 与 `?source=all` 的结果不同

**这条在开发库上无法演示**，因为目前库里只有 Mock 数据：

```
all:   1000 个商品 / 90000 个价格点
mock:  1000 个商品 / 90000 个价格点
smzdm:    0 个商品
```

隔离**机制**本身是有测试覆盖的：`test_source_filter_isolates_the_two_datasets`
在一个测试库里同时灌入两个数据源，断言 `mock=3 / smzdm=2 / all=5`，
并断言 `mock + smzdm == all`。但**可见的并排对比要等到阶段 4 真实数据进来**。

我考虑过伪造几条 `source='smzdm'` 的记录让演示好看，
**没有做**，因为 spike 只抓到过一条食品类记录（`京觅 猕猴桃`），
而项目品类是数码配件——伪造出来的对比图本身就是假证据，
而这个项目里"数据是真的还是 Mock 的"恰恰是会被面试官问到的第一个问题。

修法是阶段 4 抓完真实数据后回过头补这条验证。**在那之前，它是一处已知缺口，不是已完成项。**
